Proceed with the official ARX Smart Chart Shell buildout.

This is the chart direction we are pursuing for ARX AI.

Do not build a random standalone chart. Do not rebuild the whole app. Do not delete existing chart work. First inspect what already exists, preserve working wiring, then build the ARX Smart Chart Shell architecture on top of it.

MAIN DECISION

ARX will pursue a Smart Chart Shell with a pluggable chart-engine adapter.

The chart should be ARX-owned at the app layer, meaning ARX owns:

- the chart page structure
- symbol selection
- timeframe selection
- scanner integration
- Ruby explanation integration
- Flame Scalp markers
- Run-On Candle Momentum markers
- trade buttons
- position markers
- pending order markers
- SL/TP zones
- risk zones
- reward-to-risk visuals
- governance warnings
- provider freshness labels
- bridge connection truth
- live account truth
- role-based controls
- user-safe/admin-safe display rules

The chart-rendering engine underneath must be swappable.

Supported chart-engine path:

1. Existing ARX chart code if already present.
2. Lightweight Charts adapter as the safest beta chart renderer if needed.
3. TradingView Advanced Charts adapter only if licensing and attribution are confirmed and compliant.
4. Future full custom ARX chart engine behind the same adapter later.

The goal is not to lock ARX permanently to TradingView, Lightweight Charts, or a custom chart. The goal is to create a chart shell that lets ARX intelligence, broker truth, trade tools, and AI tools remain independent from the renderer.

PHASE 4 — BETA RENDERER DECISION

After auditing existing code, choose the best beta renderer path.

Preferred order:

1. If existing ARX chart is already functional enough, wrap it in the adapter and upgrade it.
2. If existing chart is weak or disconnected, add/upgrade a Lightweight Charts adapter as the beta renderer.
3. If TradingView Advanced Charts is already licensed/available in the project, create a TradingView adapter using a custom ARX datafeed.
4. If TradingView Advanced Charts is not licensed/available, do not fake it and do not hide TradingView branding.

Rules:
- Do not illegally hide TradingView branding/attribution.
- Do not embed TradingView as a hidden backend chart.
- Do not pretend TradingView market data is ARX broker truth.
- If TradingView is used, use it only through a compliant chart/datafeed adapter.
- ARX data must come from ARX broker/provider truth, not uncontrolled chart vendor assumptions.

PHASE 5 — DATA SOURCE TRUTH

All chart data must come through ARX truth sources.

Chart candle priority:

1. Broker-native MT5/Deriv EA Bridge v2 candles when verified and contributing.
2. Third-party composite candles only as fallback.
3. Honest unavailable/stale state when neither is trustworthy.

Chart tick/quote priority:

1. Broker/bridge tick or quote when fresh.
2. Approved provider quote fallback if broker quote is unavailable.
3. Honest stale/unavailable state when data is not trustworthy.

Rules:
- Do not label composite candles as broker-native.
- Do not mark MT5 candles contributing until real EA CopyRates candles arrive and pass validation.
- Do not show stale candles as live.
- Do not show fake candles.
- Do not show dummy price data.
- Every chart read should carry provider, freshness, and last-updated truth.
- Admin can see detailed source/freshness diagnostics.
- Normal users see simple source/freshness language only.

PHASE 10 — UI TRUTH CONTRACT

The chart must obey the ARX UI Truth Contract.

Rules:
- If account is live, active chart UI must not show paper/demo/simulation references.
- If bridge is connected and fresh, chart must not say disconnected.
- If bridge is stale, chart must show stale/reconnecting.
- If bridge is disconnected, chart must show unavailable/disconnected.
- No connected/disconnected contradiction.
- If candles are stale, chart must show stale data.
- If MT5 candles are not contributing, chart must not label candles as MT5 broker-native.
- If composite candles are used, chart must not pretend they are broker-native.
- If trade is queued, chart must not mark it filled.
- If trade is filled, chart needs broker confirmation.
- If position is closed, chart needs broker confirmation or reconciled proof.
- If position is suspect/phantom, admin should see suspect/reconciliation status.
- Ruby chart explanations must match chart data truth.
- No dummy balances.
- No fake price/candle data.
- No internal backend terms shown to normal users.

PHASE 11 — PERFORMANCE REQUIREMENTS

The chart must be fast.

Targets:
- symbol change should feel immediate
- timeframe change should load quickly
- active candle update should be near real-time when provider is fresh
- chart should not freeze scanner or Ruby
- markers should update without full chart reload when possible
- resize/mobile layout should be smooth
- crosshair/hover should not lag
- adding AI markers should not cause major re-render
- Traffic Controller should avoid unnecessary AI calls on every chart tick

Use memoization, adapter-level updates, and event-driven state carefully. Do not flood React with every tick if throttling/batching is needed.
