Goal of this phase:
Every logged-in user must only see, create, update, and delete their own app data. No route should return global trading data to a logged-in user unless it is intentionally public/system-level and documented.

Step 1 — Inventory all user-facing data:
Audit all database tables and backend routes that return or mutate user-facing data, including but not limited to:
- trading sessions
- paper trades
- trade journal
- calendar/win-loss days
- MT5 bridge status shown in app
- MT5 account snapshots
- MT5 positions
- command history
- AI analysis history
- user preferences
- dashboard cards
- notifications
- strategy/risk profiles
- watchlists
- saved setups
- receipts/logs related to trading
- any mock/demo trading data currently shown in the UI

Create a short table:
Route / table / current behavior / needs userId? / fix applied.

Step 2 — Schema migration:
Add userId ownership to every user-owned table that currently lacks it.

Requirements:
- Add userId column where needed.
- Link userId to the users table.
- Add indexes for userId and common query filters.
- Do not destroy existing data.
- For existing demo/global rows, either:
  A) assign them to a seeded demo user, or
  B) mark them as system/demo rows and exclude them from authenticated user personal views.
- Do not leak demo/global data into real user sessions unless explicitly requested as demo mode.

Step 3 — Route protection:
For every user-owned route:
- Require authenticated user.
- Use requireUser or the project’s existing auth middleware.
- Scope all SELECT queries with userId = req.authUser.id.
- Scope all UPDATE/DELETE mutations with userId = req.authUser.id.
- Scope all INSERT/CREATE actions to automatically set userId = req.authUser.id.
- Never accept userId directly from the client for ownership unless admin-only and explicitly validated.

Step 4 — Frontend wiring:
Update the frontend only where needed so it uses the logged-in user’s scoped data.

Requirements:
- Do not hardcode fake personal data.
- If no user data exists, show a clean first-time-user state.
- First-time user state should say things like:
  “No trading sessions yet”
  “Connect MT5 to begin tracking”
  “No trades recorded yet”
  “Your calendar will populate after your first session”
- Do not show stale global/demo trading data as if it belongs to the user.

Step 5 — Protect MT5 bridge display without implementing Phase 3 yet:
For this phase, do not fully build per-user MT5 connections yet. But prevent the frontend from showing another user/global MT5 connection as personal.

Until Phase 3 is implemented:

- Personal dashboard should not claim “your MT5 connected” unless the connection is tied to the logged-in user.
- Keep bridge backend endpoints working.
- Do not break /api/mt5/heartbeat/status or /api/mt5/bridge-diagnostics.
