Phase 22H — Real AI Provider + App Knowledge Brain

Before making changes, inspect Phase 22F and 22G results. Do not continue if:
- assistant tool routing is not working
- Live Mode/voice bypasses the backend assistant route
- assistant can still fabricate market, bridge, notification, journal, risk, or prop firm data
- frontend chat is still relying on fake/static assistant replies

Goal:
Make the ARX AI assistant truly powered by the backend AI provider, real app tools, and a canonical app knowledge system. The assistant should be able to answer questions about the app, current page, buttons, features, user setup status, and trading systems without guessing.

This phase is not for redesigning UI.
This phase is not for building live trade execution.
This phase is not for fake demo intelligence.

Core goals:
- Verify real OpenAI/provider wiring.
- Keep API keys backend-only.
- Remove/disable mock assistant behavior unless explicitly marked dev-only.
- Preserve Phase 22F tool routing.
- Preserve Phase 22G live chat and voice behavior.
- Add a canonical app feature registry.
- Add assistant tools for app knowledge and page help.
- Make fresh users get honest first-time guidance.
- Make returning users get personalized, scoped guidance.

2. Real AI provider configuration check

Create or strengthen backend-only AI provider setup.

Support environment variables if not already supported:
- `OPENAI_API_KEY`
- `OPENAI_MODEL` or existing project model env if already used

Rules:
- Never expose `OPENAI_API_KEY` to frontend.
- Never log full API keys.
- Never hardcode real keys.
- If no provider key exists, assistant status must say AI provider is not configured.
- If provider is configured, assistant status may show provider name and model name only if safe.
- Do not break existing provider setup if it already exists.
- Do not replace working code unnecessarily.

3. Assistant provider status endpoint

Add or update an authenticated endpoint:

`GET /api/me/assistant/provider-status`

Expected safe response:
{
  provider: "openai" | "none" | "unknown",
  configured: boolean,
  connected: boolean,
  model: string | null,
  streamingEnabled: boolean,
  toolCallingEnabled: boolean,
  keysExposed: false,
  lastCheckedAt: string,
  notes: string
}

Rules:
- Requires authenticated user.
- Does not expose secrets.
- Does not claim connected if the provider cannot be verified.
- Does not claim streaming is enabled unless the current assistant route actually supports it.

7. Add assistant app-knowledge tools

Add/register these assistant tools if missing:

`getAppFeatureRegistry`
- Returns safe feature list and status.
- Requires auth if user-specific statuses are included.
- Does not expose secrets or raw code.

`getFeatureHelp`
- Accepts featureId or featureName.
- Returns what the feature does, where to find it, setup requirements, and current status.

`getCurrentPageHelp`
- Accepts current route/page context from frontend.
- Explains what the current page is for, what actions are available, and what setup is missing.

`getAssistantCapabilityStatus`
- Returns what the assistant can currently do:
  - app help
  - market awareness
  - bridge awareness
  - risk checks
  - journal analysis
  - notifications
  - voice input
  - speech output
  - live mode
  - unavailable capabilities

10. Fresh-user onboarding intelligence

For brand-new users, assistant should truthfully guide setup.

Fresh user should be told:
- no trades yet
- no notifications yet
- no journal data yet
- risk settings may need setup
- MT5 bridge may need connection
- market provider may not be connected
- push may not be configured/enabled
- paper/demo mode status
- next recommended setup steps

Do not show fake trade history, fake alerts, fake market data, or fake performance.

11. Returning-user personalization

For returning users, assistant should use only their scoped data.

It may explain:
- current setup status
- unread notifications
- bridge status
- market provider status
- risk configuration
- journal/performance availability
- prop firm mode status
- coaching readiness

Cross-user data must never appear.

12. Trading education safety

For general trading questions:
- assistant may provide educational explanations
- assistant must not give guaranteed-profit claims
- assistant must not claim perfect entries
- assistant must not claim live market conditions without market tools
- assistant must say when market provider is disconnected/stale
- assistant must run risk tools before saying a specific trade is ready
- assistant must separate paper/demo from live trading
