Read this entire command before changing anything.

There is one root cause behind the current symptoms: some surfaces still emit confident market reads or setup details while other surfaces correctly say the chart/feed is unconfirmed or insufficient.

The most dangerous case is Ruby chat giving a full decimal trade setup — entry, stop loss, TP1, TP2, TP3, R:R — while the Ruby Chart Read panel says chart intelligence is unavailable or feed is not confirmed.

Fix this as one consistency task.

This is not a cosmetic copy change. The verdict must be enforced in code.

## Part B — Enforce sufficiency at the Ruby/chat tool boundary

The setup-building path must compute the same shared selected-symbol + selected-timeframe sufficiency verdict that the chart/Ruby panel uses.

When the verdict does not permit a directional setup:

- Do not compute entry.
- Do not compute stop loss.
- Do not compute take-profit levels.
- Do not compute risk/reward.
- Do not return hidden levels in alternate fields.
- Do not return partial decimal setup levels.
- Return a withheld state instead.

Returned withheld state must include:

- withheld: true, or equivalent
- symbol
- timeframe
- shared insufficiency reason
- the same human-readable reason the chart/Ruby read shows
- safe message: “I can’t give a trade setup until chart/feed sufficiency is confirmed.”

The model must not be trusted to withhold levels from a prompt instruction. The code must not provide the levels.

### Required behavior

If chart/Ruby sufficiency is insufficient, stale, partial, unconfirmed, blocked, syncing, or no-AI:

Ruby may say:

- “I can’t give entry/SL/TP yet because chart data is not confirmed.”
- “The scanner leans bullish/bearish, but setup levels are withheld until feed confirmation.”
- “Decision support only; wait for confirmed candles.”

Ruby must not say:

- “Entry is…”
- “Stop loss is…”
- “TP1/TP2/TP3 are…”
- “Risk/reward is…”
- any decimal setup plan

### buildSetupPreview fail-closed requirement

buildSetupPreview is documented as turning a verified chart read into a setup preview.

That is not enough.

Either:

1. Add fail-closed protection inside buildSetupPreview so it refuses or returns withheld when the input is unverified/insufficient.

Preferred.

or:

2. Prove every call site checks the shared sufficiency verdict before calling buildSetupPreview.

If choosing option 2, add tests proving no unverified call site can invoke it.
