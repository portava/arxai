# COMMAND — VOLATILITY SYSTEM: ONE TRUTH FOR SYNTHETIC FEEDS, THEN LIVE ENTRY

Read this entire command before changing anything. Two phases, in order: PHASE 1 makes the synthetic (Deriv volatility) feed state HONEST and consistent across every volatility surface; PHASE 2 lets a *genuinely* live-confirmed synthetic feed reach the live-entry path through the EXISTING gated pipeline. Phase 2 depends on Phase 1 being correct. Do not start Phase 2 until Phase 1 passes. Do not mark complete until the COMPLETION STANDARD passes with pasted evidence.

## THE CONTRADICTION (verified on live screenshots, Jun 14, V75(1s) 30m)

The Ruby Chart Read feed popup for "Volatility 75 (1s) Index" shows, in ONE panel:
- State: **Live**, Source: deriv, Latency: 268 ms, Last candle: **just now**, Last tick: **3–7s ago**, Missing candles: **0**, Readiness: **LIVE_FEED**
- AND: AI-usable: **Not confirmed**

…while the page above it says "Historical data — analysis only", "Live feed unavailable · Analysis only", "Data is incomplete — historical context only, not valid for a live entry."

A feed cannot be both "Live, last candle just now, 0 missing" and "unavailable / historical only" for the same symbol at the same instant.

## ROOT CAUSE (already traced in source — do not re-litigate the location)

Two DIFFERENT scopes of "is there a recent tick" feed the two halves:

- The popup's "State / Last tick / Readiness LIVE_FEED" come from **`getDerivFeedStatus()`** (`lib/data/providers/derivProvider.ts` ~L139), which uses **`client.hasRecentTick()` — a GLOBAL check** (true if ANY subscribed synthetic ticked recently).
- The "AI-usable / not-confirmed → historical-only" downgrade comes from the **PER-SYMBOL** gate **`hasRecentDerivTickFor(symbol, 30_000)`** (~L92), which checks the cached tick for THAT EXACT Deriv id (`getCachedTickByDerivId(resolveDerivSymbol(label).derivId)`). Its own comment: "so one ticking symbol does NOT promote the rest." This sets `syntheticAwaitingTick` in `chartDataService.ts` (~L225 `hasLiveTick = hasRecentDerivTickFor(symbol)`), which forces `classifyCandleFreshness` to at-least "delayed" → `buildFeedStatus` sets `aiUsable = (quality === "clean") = false` (`lib/data/freshness.ts` ~L118-122, L297).

So the popup shows the GLOBAL feed is live while the PER-SYMBOL gate says THIS symbol (V75 1s) has no recent tick. Both can be internally "correct" yet the screen is a lie.

### 1B. One per-symbol synthetic verdict, consumed by every surface
There must be a single per-symbol synthetic feed verdict (live-confirmed / awaiting-tick / stale / unavailable), derived from the SAME per-symbol signal, that EVERY volatility surface reads:
- the feed-status popup ("State / Last tick / AI-usable / Readiness")
- the chart "Live feed unavailable · Analysis only" / "LAST-KNOWN" banner

If V75(1s) is individually live, all of them say live; if it's individually awaiting, the popup honestly says "awaiting a confirmed live tick for THIS symbol" instead of a misleading global "Live · just now." Same one-truth principle as Task #512, extended to the synthetic per-symbol case. No surface computes its own synthetic feed verdict.

### 1C. The fix must be DIRECTIONALLY CORRECT — not permissive
This is non-negotiable: the gate must become *accurate*, not *lenient*.
- A genuinely live per-symbol synthetic (recent per-symbol tick, 0 missing, fresh) → reads LIVE_CONFIRMED / AI-usable.
- A synthetic that genuinely has history but NO recent per-symbol tick → still reads awaiting/historical and is NOT AI-usable.
- One ticking synthetic must NOT promote a non-ticking one (preserve the existing per-row isolation).
You are fixing false-negatives (genuinely-live read as historical). You must NOT introduce false-positives (historical read as live). Do not "resolve" the contradiction by blanket-treating synthetics as always-live.

## PHASE 2 — OPEN LIVE ENTRY FOR GENUINELY-LIVE SYNTHETICS (existing gates intact)

Only after Phase 1: when the corrected per-symbol synthetic verdict is genuinely LIVE_CONFIRMED, the scanner/entry surfaces may treat that synthetic as a valid live-entry feed — lifting the "Approval required — trading isn't available from the scanner in this mode" / "historical only, not valid for a live entry" block for that symbol.

### NON-NEGOTIABLE RULES FOR PHASE 2
- The existing server-side execution gates run UNCHANGED on every synthetic order — the 16-gate evaluator, per-click lot caps, master-live access, kill switch, rate limit, exposure reservation. Lifting the feed-state block does NOT bypass, weaken, or skip any of them. Grep the live pipeline and confirm the synthetic path flows through the SAME `createLiveDraft → confirmLiveCommand → dispatchLiveCommand` gate chain as everything else — no synthetic-specific shortcut.
- The block lifts ONLY when the feed is genuinely live-confirmed per Phase 1. An awaiting/stale synthetic STILL blocks entry, with the honest reason shown. (Fixing false-negatives, not creating false-positives — same as 1C.)
- Human confirmation at the broker boundary stays. "Live entry available" means the Plan/Build → confirm flow becomes available; it does NOT mean an order fires on tap, and it does NOT arm one-click. Do not remove or auto-satisfy the confirmation step.
- No AI/Ruby auto-execution. Ruby giving a live read on a now-confirmed synthetic is fine; Ruby placing the order is not — that stays behind its existing explicit per-user flags. Lifting the feed block must not enable AI-initiated execution.
- STOP-LOSS POLICY APPLIES TO SYNTHETICS. Opening this path must NOT relax `requireStopLoss` / `allowOrdersWithoutStopLoss`. (Evidence this matters: the live screenshots show an open V75 position with NO stop-loss and "downside is uncapped." Making synthetics easier to enter makes the SL gate MORE important, not less.) Confirm the SL policy gate is enforced on the synthetic entry path; do not carve out an exception.
- No global live-exec setting changes. Scope strictly to letting a confirmed-live synthetic feed be a valid entry feed.
