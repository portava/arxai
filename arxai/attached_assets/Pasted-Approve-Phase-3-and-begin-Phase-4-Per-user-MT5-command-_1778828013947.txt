Phase 4A — Command ownership model:
Audit/create the MT5 command queue table.

Each command should include:
- id
- userId
- mt5ConnectionId
- tradingSessionId nullable
- commandType
- payload
- status: pending / claimed / sent / completed / failed / expired / cancelled
- requestedByUserId
- requestedAt
- claimedAt
- completedAt
- failedAt
- expiresAt
- resultPayload
- errorMessage
- safetyMode: paper_only / read_only / live_locked
- createdAt
- updatedAt

Requirements:
- Every command must belong to a userId.
- Every command must target one mt5ConnectionId.
- Commands must never be global unless explicitly marked as system/demo and excluded from user personal EA polling.
- Never accept userId from frontend for ownership. Use req.authUser.id.

Phase 4B — Scope GET /api/mt5/commands by bridge token:
Update GET /api/mt5/commands so the EA must send:

Header:
X-MT5-Bridge-Token: <connection token>

Backend must:
1. Hash the token.
2. Find the matching mt5_connections row.
3. Reject invalid or revoked token.
4. Use the matched connection’s userId and mt5ConnectionId.
5. Return only pending commands for that userId + mt5ConnectionId.
6. Never return another user’s commands.
7. Mark returned commands as claimed/sent safely if current system uses claim semantics.
8. Keep response shape compatible with the existing EA if possible.

If current EA does not send token on command polling, report that clearly and add backend-safe support only if the EA already has the token available. Do not silently fall back to global commands.

Phase 4C — Scope POST /api/mt5/command-result:
Update command-result handling so EA result submissions are also token-scoped.

Backend must:
1. Require X-MT5-Bridge-Token.
2. Hash and match token to mt5Connection.
3. Only allow result update for commands owned by that matched userId + mt5ConnectionId.
4. Reject attempts to complete another user’s command.
5. Store resultPayload and errorMessage safely.
6. Never expose raw bridge token.
