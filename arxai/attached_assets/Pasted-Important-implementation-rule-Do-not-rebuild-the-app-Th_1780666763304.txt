Important implementation rule:
Do not rebuild the app.

This is an upgrade to the existing ARX AI system, not a replacement, rewrite, redesign, or rebuild.

Preserve the current app architecture, routes, components, services, hooks, database models, live bridge flow, scanner flow, Ruby flow, Smart Chart flow, trade modal flow, admin/user/investor role system, and all existing permissions.

Before changing anything:
1. Inspect what already exists.
2. Identify the current source of truth for each function.
3. Reuse existing code wherever possible.
4. Upgrade missing pieces only.
5. Do not duplicate services.
6. Do not create parallel systems that conflict with existing ones.
7. Do not remove current functionality to make the upgrade easier.
8. Do not break the live execution path.
9. Do not break scanner, Ruby, Smart Chart, trade modal, open positions, retcodes, investor portal, admin controls, or role permissions.

This upgrade must make the entire system more connected.

Build an internal ARX Handshake System so every major layer checks in with the others before producing user-facing analysis, trade previews, alerts, investor reporting, or admin decisions.

The purpose of the handshake system:
Every layer, function, module, and agent should know whether the required connected systems are available, fresh, valid, and aligned.

Ruby should not give a signal unless scanner data, chart data, symbol specs, broker state, news context, execution conditions, user/account permissions, and risk logic have checked in successfully.

Investor values should not update unless investor ledger, NAV engine, broker mirror, pool allocation, lock status, fee logic, and reconciliation status have checked in successfully.

Trade preview should not open unless signal state, symbol specs, account state, execution cost, slippage, SL/TP validation, bridge readiness, and permissions have checked in successfully.

PART 4 — REQUIRED HANDSHAKE TYPES
====================================================

Implement at least these handshake types:

1. Scanner Signal Handshake
Used before Ruby presents scanner signal as actionable.

Must check:
- live price freshness
- candle data freshness
- symbol specs available
- selected symbol valid
- scanner result available
- signal lifecycle state
- late/do-not-chase status
- news risk
- spread/slippage conditions
- execution cost viability
- risk/reward viability
- Ruby explanation ready
- chart overlay sync
- user permissions if trade action is shown
- bridge readiness if Build Trade is shown

2. Smart Chart Overlay Handshake
Used before chart overlays are drawn.

Must check:
- chart data loaded
- selected symbol matches scanner symbol
- Ruby signal exists
- levels/zones available
- news events mapped to symbol
- execution cost data available if layer enabled
- trade health data available if open position exists
- overlay timestamps/freshness

3. Trade Preview Handshake
Used before opening Build Trade / trade modal from Ruby/scanner/chart.

Must check:
- signal not stale
- signal not late unless user is only reviewing
- symbol specs available
- bid/ask fresh
- spread acceptable
- slippage estimate available
- lot size valid
- SL/TP valid
- margin sufficient
- account live-enabled if live
- user allowed to trade
- bridge ready
- kill switch off
- no critical discrepancy
- no conflicting open trade warning unacknowledged if applicable

4. Live Trade Health Handshake
Used after trade is open.

Must check:
- position exists in broker/EA position sync
- position freshness
- selected symbol matches
- TP/SL known
- current price fresh
- Ruby original signal available if trade came from Ruby
- trade health engine active
- retcode/fill data stored
- slippage actual vs estimate if available

5. Investor Value Handshake
Used before displaying investor balance/current value.

Must check:
- investor ledger scoped to authenticated investor
- investor holdings loaded
- current NAV available
- broker mirror overlay available if applicable
- pool assignments valid
- locked funds calculated
- available withdrawal calculated
- fees applied
- reconciliation passed or status shown
- no critical discrepancy
- investor cannot see other investor data
- ARX internal waterfall hidden

6. Weekly Investor Report Handshake
Used before publishing weekly account story/report.

Must check:
- weekly NAV close completed
- broker sync fresh/reconciled
- investor ledger reconciled
- P/L calculation completed
- fees calculated
- locked deposit status included
- economic/news attribution available or marked unavailable
- no stale data
- no critical discrepancy
- report visible only to correct investor
- ARX internal waterfall excluded

7. Admin Fund Control Handshake
Used before admin approves deposits/withdrawals/waterfall/adjustments.

Must check:
- admin permission
- audit logging available
- affected investor/pool data loaded
- reconciliation status
- lock/freeze status
- required reason/note captured
- action does not violate policy

8. Ruby Explanation Handshake
Used before Ruby answers scanner/trade questions.

Must check:
- market data context
- scanner context
- chart context
- news/economic context
- symbol-specific playbook
- execution/risk context if trade-related
- user role context
- no internal wording leakage
- explanation includes required fields

====================================================
PART 6 — HOW HANDSHAKE SHOULD AFFECT USER UI
====================================================

The handshake should produce clean user-facing states.

Examples:

Scanner:
If scanner data is fresh but news risk is high:
“Setup forming, but news risk is high. Ruby is watching zones, not recommending entry yet.”

If price signal is late:
“Late — do not chase. Price moved too far from Ruby’s entry zone.”

If market data is stale:
“Waiting for fresh price before Ruby updates this signal.”

Smart Chart:
If news event mapped:
“USD CPI in 12 minutes — high impact for Gold/EURUSD/US30.”

Trade Preview:
If SL/TP invalid:
“Ruby needs a valid stop loss and take profit before this trade can be reviewed.”

If bridge not ready:
“Live bridge is not ready. Ruby can analyze but cannot prepare live execution.”

Investor:
If reconciliation passed:
“Portfolio Status: Fresh.”

If broker sync stale:
“Portfolio update delayed. Values may change after broker sync completes.”

Admin:
If discrepancy blocks payout:
“Critical discrepancy detected. Withdrawals and weekly report publishing are paused until resolved.”

====================================================
PART 7 — HANDSHAKE SHOULD NOT BECOME A HARD BLOCK EVERYWHERE
====================================================

Use blocking only when necessary.

Blocking examples:
- stale trade signal used for live trade
- missing symbol specs for lot/slippage calculation
- invalid SL/TP
- insufficient margin
- investor data mismatch
- critical discrepancy
- user lacks permission
- bridge not ready for live trade
- kill switch active
- locked funds withdrawal attempt

Warning examples:
- news risk high
- spread elevated
- explanation partial
- economic driver unknown
- chart overlay missing non-critical layer
- confidence mixed
- broker sync delayed but investor value clearly marked under review

Degraded mode:
If news is unavailable, Ruby can still analyze technicals but must say:
“No confirmed news driver available from current data.”

If slippage history unavailable, Ruby can estimate from spread/volatility and say:
“Slippage estimate is based on current spread and volatility because recent execution history is unavailable.”
