- After AI finishes speaking, resume listening automatically.
- Keep conversation memory per user/session.

STEP 2 — MAKE AUTO-LISTEN DEFAULT WHEN AI POPUP OPENS

Required behavior:

When ARX AI popup opens:
1. If microphone permission is already granted:
   - automatically start listening.
   - show “Listening…” or “Mic on.”
   - auto-listen should be active by default.

2. If microphone permission is unknown:
   - show a clean one-time prompt/button:
     “Enable microphone to talk to ARX.”
   - after user grants permission, start listening automatically.

3. If microphone permission is denied:
   - show:
     “Microphone access is blocked. Enable it in browser settings to use voice.”
   - text chat must still work.

4. If popup closes:
   - stop listening immediately.
   - stop recording immediately.
   - release all microphone tracks.
   - cancel VAD loop.
   - clear timers.
   - do not listen in background.

IMPORTANT UI CHANGE:
Since the user wants the AI to auto-listen whenever open, do not make “Auto-listen: off” the default visible state.

Use cleaner states:
- “Listening…” when waiting for voice
- “Hearing you…” when speech is detected
- “Processing…” when sending to AI
- “Speaking…” when AI is talking
- “Mic off” only when user manually disables mic
- “Mic permission needed” when permission is not granted

If you keep the auto-listen pill, default it to ON after permission is granted. The mic button should act as a manual mute/off switch, not the primary way to start the assistant.

STEP 3 — IMPLEMENT TRUE VOICE ACTIVITY DETECTION

Use Web Audio API / AnalyserNode or existing VAD if already present.

The voice loop should work like this:
1. Popup opens.
2. Start listening.
3. Calibrate room noise for 500–800ms.
4. Detect speech above dynamic noise threshold.
5. Begin recording when speech is detected for 250–400ms.
6. Continue recording while user is speaking.
7. Stop recording after 900–1300ms of silence.
8. Ignore clips under 400ms.
9. Hard stop clips at 15 seconds.
10. Send one request per spoken command.
11. Do not send duplicate requests.
12. Do not cut off the first word if possible.

Use compressed audio format where supported:
- audio/webm;codecs=opus preferred
- fallback safely for Safari/iPhone if needed

STEP 4 — AI SPEAKBACK MUST WORK

When Speak is on:
- AI must speak its response out loud.
- Text response should still appear in chat.
- Voice playback should not block the UI forever.
- Show “Speaking…” while audio plays.
- When audio ends, return to listening automatically.

Implement or fix TTS flow:

Option A if backend already supports TTS:
- call existing TTS endpoint with final assistant text.
- receive audio blob.
- play it in frontend.
- handle audio ended event.
- resume listening.

Option B if realtime already returns audio:
- play realtime audio response correctly.
- attach audio stream/output to browser playback.
- resume listening after playback ends.

Option C fallback:
- use browser SpeechSynthesis only as a temporary fallback if backend TTS fails.
- label this as fallback in code.
- do not let TTS failure break text chat.

Required TTS safety:
- If Speak is off, do not play audio.
- If Speak is on but TTS fails, still show text response.
- Do not show raw errors.
- Do not leave status stuck on “Speaking…”

STEP 5 — PREVENT AI FROM RECORDING ITSELF

When AI is speaking:
- pause microphone listening/VAD.
- do not record AI audio.
- resume listening only after AI audio ends.
- if user taps mic while AI is speaking, stop AI audio and listen to user.

This prevents feedback loops.

STEP 6 — MAKE VOICE AND TEXT USE THE SAME AI BRAIN

Voice transcript must go through the exact same route/context as typed messages.

Do not create separate isolated voice prompts.

Every AI request should include:
- userId if logged in
- anonymousSessionId if not logged in
- conversationId
- recent chat history
- last user message
- last assistant response
- pendingAction/unresolved tool request
- current page/app context
- market/MT5 status

Typed chat, voice chat, and quick suggestions must all share the same memory and routing.

STEP 7 — ADD PERSISTENT USER CONVERSATION MEMORY

User wants AI to remember all user conversations.

Implement memory safely and per-user:

A. Logged-in users
Store conversation history in database by:
- userId
- conversationId
- role: user/assistant/tool/system-safe-summary
- message content
- timestamp
- channel: text/voice/quick_suggestion/tool
- metadata: page, tool used, market status, pending action status

B. Anonymous users
Use anonymousSessionId for temporary memory.
Persist locally or server-side session memory.
When user logs in, optionally merge anonymous session into their account if safe.

C. Long-term memory summary
To avoid sending huge histories every request:
- keep recent 10–20 turns in prompt
- maintain a compact rolling summary per user
- track unresolved requests/pendingAction separately
- store important preferences and app setup facts separately

D. User isolation and privacy
- Never mix conversations between users.
- Never expose another user’s history.
- Add ability to delete/clear conversation history later.
- Do not store raw audio unless explicitly needed. Prefer storing transcript + metadata.
- Use secure database access rules.
