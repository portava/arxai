T016 — NO-FEATURE-CHANGE PERFORMANCE ARCHITECTURE AUDIT + SAFE OPTIMIZATION PASS

Continue from T015/T014 readiness work.

Product direction:
ARX AI is LIVE-first for owner/admin operation.
Do not suggest Demo.
Do not use Paper Trading.
Do not use fake execution.
Do not use simulated trade data.
Do not add new product features unless they replace/remove a redundant feature.

This is not a rebuild.
Do not redesign the app.
Do not duplicate Scanner, Ruby, MT5 bridge, trade execution, auth, admin, account modes, or ledger systems.
Do not change the product’s active feature set except removing, hiding, collapsing, or archiving redundant/dead/non-product surfaces.
Do not place a live trade in this task.
Do not reset live broker execution config.
Do not weaken permissions, ownership checks, kill switch, allocation checks, freeze checks, live approval, or MT5 confirmation rules.
Do not bypass safety to gain speed.

Goal:
Make ARX AI faster and more efficient without changing the app’s intended functionality.

This pass should focus on four lanes:

1. Measure — preserve/add real browser timing and route/action performance visibility.
2. Defer — move noncritical work after first paint.
3. Reduce — remove duplicate work, duplicate fetches, dormant UI, and repeated renders.
4. Protect — keep live trading safety, server-side filtering, route containment, and MT5 truth intact.

Core performance standard:

1. Bottom-nav tap feedback under 100ms.
2. Page shell visible under 1 second.
3. Scanner shell visible under 1 second.
4. Chart skeleton visible under 1 second.
5. Symbol search usable under 1 second.
6. Market selection feedback under 300ms.
7. Buy/Sell modal open under 1 second.
8. Trade pending state under 100ms after Confirm.
9. Ruby thinking dots under 100ms.
10. No page feels frozen.
11. Slow external calls must show immediate loading/pending state.

PART 1 — Start with runtime health

Run first:
pnpm run health:workflows

Confirm:

1. frontend serving
2. api-server serving
3. /api/healthz 200
4. Scanner candles auth behavior correct
5. no stale/orphaned workflow issue
6. bridge/EA heartbeat visible where applicable
7. live MT5 path healthy
8. no live trade placed

If workflow health fails:

1. Do not continue to performance changes.
2. Fix workflow/runtime health first.
3. Do not disturb live MT5 unless the health failure directly requires it and operator approval exists.
4. Report exact failure.

6. One failed widget must not fail the whole page.
7. Normal trading actions must remain available.

PART 5 — Safe optimization lane: Reduce duplicate work

Find and fix duplicate or unnecessary work.

Check for:

1. repeated auth/session requests on route change
2. repeated account-mode requests
3. repeated bridge health polling
4. repeated scanner calls
5. repeated notification calls
6. duplicate route data calls
7. duplicate React Query keys
8. overly aggressive refetchOnWindowFocus
9. unnecessary refetch on tab switch
10. components remounting when they should update
11. full Scanner rerender when Ruby changes
12. chart remount when only quote changes
13. trade modal remount when only input changes
14. admin data loaded for normal users
15. hidden tabs rendering heavy content
16. unbounded long lists rendering all at once

Fix safely:

1. batch duplicate calls
2. cache safe static metadata
3. set proper staleTime where appropriate
4. disable refetchOnWindowFocus only where safe
5. pause polling on hidden tabs
6. debounce search
7. cancel stale search/scanner requests
8. memoize heavy components
9. split context providers if one global context rerenders the whole app
10. virtualize long lists if needed
11. create stable query keys
12. avoid chart remounts; update series/markers incrementally

Do not cache user-specific trade data in a way that can leak between users.
All trade data must remain server-filtered.

PART 6 — Safe optimization lane: Chart and Scanner efficiency

Scanner must stay the fastest trading surface.

Requirements:

1. Scanner shell renders first.
2. Chart skeleton renders fast.
3. Search is usable fast.
4. Buy/Sell controls appear fast.
5. Quote/candles load independently.
6. User trade overlays load independently.
7. Broad/Focus Scan load independently.
8. Ruby explanation loads independently.
9. News/history/backtest load after main UI.
10. Notification badge does not block Scanner.

Chart rules:

1. Do not remount the chart for every quote.
2. Do not remount the chart because Ruby updates.
3. Do not remount the chart because notifications update.
4. Update candle series incrementally.
5. Update price lines/markers incrementally.
6. Throttle or debounce noncritical overlay updates.
7. Keep chart state separate from Scanner result state.
8. Keep trade overlay state server-filtered.

PART 7 — Safe optimization lane: Ruby efficiency

Ruby must feel instant without blocking trading.

Requirements:

1. Ruby thinking dots appear under 100ms.
2. Ruby shell opens quickly.
3. Ruby response may take longer, but UI must not freeze.
4. Ruby should stream or progressively render if supported.
5. Ruby should reuse current chart/scan state instead of refetching whenever safe.
6. Ruby memory/history loads after shell.
7. Ruby memory writes happen after user-visible response where safe.
8. Ruby must not block Scanner render.
9. Ruby must not block trade Confirm.
10. Ruby must not bypass backend permissions.

PART 8 — Safe optimization lane: Backend/event-loop efficiency

Inspect backend for blocking work on critical paths.

Critical live trade path should stay lean:

1. auth
2. permission
3. allocation
4. kill switch
5. freeze check
6. symbol/lot validation
7. bridge readiness
8. MT5 dispatch
9. ledger write
10. response

Move outside critical path where safe:

1. Ruby explanation
2. news analysis
3. historical backtest
4. deep scan scoring
5. admin log enrichment
6. noncritical notifications
7. performance summaries
8. long diagnostics

Check for:

1. synchronous heavy loops
2. blocking JSON parsing/stringifying
3. huge response payloads
4. large unpaginated queries
5. expensive logs before response
6. slow external calls without timeout
7. duplicate bridge calls
8. retrieving master trades when only user-filtered trades are needed

Do not remove backend validation.
Do not move security validation to frontend.
