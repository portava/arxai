MAJOR FIX: Scanner truth-state errors + candle history depth + feed reliability audit.

This is not a cosmetic fix. The screenshots show serious data, feed, chart, Ruby, scanner, and execution-state contradictions. Fix this as a full scanner/chart/feed integrity repair.

Current visible problems from screenshots:
1. App says LIVE · Shared MT5 while the selected market says Historical only.
2. Trading says Enabled while selected symbol execution may not be available through current MT5 bridge.
3. Ruby says Limited read but Ruby Market Read also shows green “Live feed updated.”
4. Chart says last-known / live feed unavailable while still rendering candles like active data.

9. Only a few hours of candles are available on some timeframes.

11. Users cannot scroll back far enough.
12. Candles are still not fully reaching the app.

Primary goal:
Fix the entire market data pipeline so ARX AI has reliable, deep, scrollable candle history for every supported market/timeframe, while the UI truthfully separates:
- global bridge live status
- selected symbol data status
- selected symbol execution status
- Ruby read/actionability status
- chart history depth
- broker symbol specs readiness

Do not redesign the screen yet. This is a data integrity, feed reliability, chart history, and truth-contract fix.

====================================================

This is critical.

Users must be able to scroll back far into chart history. A few hours or a few days is not acceptable.

Required chart history targets:

- 5m: minimum 90 days available
- 15m: minimum 180 days available
- 1h: minimum 1 year available

- 1D: minimum 5 years available if provider supports it

For forex/metals/indices/crypto:
- 1m: minimum 30 days
- 5m: minimum 90 days
- 15m: minimum 180 days
- 1h: minimum 1 year
- 4h: minimum 2 years
- 1D: minimum 5 years

If provider cannot supply that much, the API must return:
- provider limit
- actual oldest candle
- actual candle count
- reason
- next available source fallback

Do not silently show only a few hours.

Do not rely only on live frontend fetches.

Create a candle storage/cache layer:
- Store candles by symbol + timeframe + source + time.
- Use unique key: symbol/timeframe/time/source.
- Prevent duplicates.
- Upsert newer candles.
- Backfill older candles on demand.
- Cache successful provider responses.
- Use stored candles immediately while fetching fresh ones.
- Mark cache freshness.

Preferred backend service:

  symbol,
  timeframe,
  limit,
  before,
  after,
  sourcePreference

It should:
1. Check local database/cache first.
2. Return cached candles quickly.
3. Fetch missing older candles from provider.
4. Merge provider candles into cache.
5. Return unified ordered candles.
6. Include freshness/depth metadata.

====================================================

Audit:
- WebSocket/SSE lifecycle
- reconnect logic

- Replit server sleep/restart behavior
- provider rate limits
- API failures
- symbol mapping failures
- stale heartbeat handling

- query cache invalidation

Add robust reconnect:
- exponential backoff
- automatic resubscribe to selected symbol/timeframe
- heartbeat monitor
- stale timer
- visible reconnecting badge
- do not erase existing candles when feed drops
- keep last-known candles but label them stale
- resume live updates when feed returns

Feed state rules:
- If live feed drops, keep chart visible but mark stale.
- Do not switch to fake live.
- Do not clear candles unless symbol/timeframe changes.
- If new candles stop arriving past expected interval, mark stale.
- When feed returns, append missing candles/backfill gap.

Expected stale thresholds:
- 1m: stale if no candle/tick update beyond 2–3 minutes
- 5m: stale if no candle/tick update beyond 7–10 minutes
- 15m: stale if no update beyond 20 minutes
- 1h: stale if no update beyond 70 minutes
- 4h: stale if no update beyond 5 hours
- 1D: stale if no update beyond 36 hours

For tick/live quote feeds, use a much shorter stale threshold where available.
