STEP 2 — ONLY PATCH GAPS FOUND IN AUDIT

After the audit, patch only the missing or broken pieces. Do not replace working systems.

Required behavior after patch:

1. Short follow-up resolver
Messages like:
- “?”
- “??”
- “and?”
- “so?”
- “what happened?”
- “did you check?”
- “what did you find?”
- “you didn’t answer”
- “I asked you a question”
- “right now?”

must resolve against the most recent unresolved user request or pending action.

For the exact case:
User: “Check scanner and tell me what market is good to trade right now.”
Assistant: “Let me check…”
User: “?”

ARX should follow up on the scanner request, not explain the page.

2. Pending action tracking
If not already implemented, add a lightweight pendingAction object.

Example:
{
  "type": "market_scanner",
  "status": "pending" | "running" | "completed" | "failed",
  "userIntent": "find good market to trade right now",
  "lastAssistantPromise": "Let’s take a look at the market scanner...",
  "requiredData": ["scanner_results", "market_data"],
  "blockingIssue": null
}

When ARX says it is going to check something, it must either:
- call the related endpoint/tool and return a result, or
- immediately explain why it cannot.

Do not leave unresolved “give me a moment” responses.

3. Chat history/session memory
If chat history is not already sent/stored, add it.

Requirements:
- Use logged-in userId if available.
- Use anonymous sessionId if user is not logged in.
- Send recent 10–20 chat turns or compact history summary to backend.
- Include last user request.
- Include last assistant response.
- Include last unresolved action.
- Use the same context for typed messages, voice transcripts, and quick suggestions.

4. Fix getCurrentPageHelp routing
getCurrentPageHelp should only trigger for clear page-help requests, such as:
- “What page am I on?”
- “Explain this page”
- “How do I use this screen?”
- “What does this button do?”
- “Help me with this dashboard”

It must NOT trigger for:
- “?”
- “and?”
- “what happened?”
- “I asked you a question”
- scanner requests
- trade opportunity requests
- MT5 bridge questions
- risk questions

5. Scanner behavior
Check whether a real scanner endpoint exists.

If scanner data exists:
ARX should return ranked paper-trade candidates with:
- symbol
- direction bias
- setup type
- confidence
- risk level
- reason
- invalidation condition
- paper-only warning

If market data is disconnected:
ARX should say:
“Market data is not connected yet, so I can’t honestly tell you the best market right now. Connect MT5 or a live data feed, then I can scan live conditions. For now, I can help you choose what to watch based on your trading style.”

If scanner backend is not ready:
ARX should say:
“The scanner backend is not fully wired to live data yet. I can see the scanner intent, but I can’t return real candidates until the scanner endpoint is connected.”

Do not fake candidates.

6. Trading answer safety
When user asks what to trade right now:
- check scanner/market data first
- do not guarantee profit
- do not say “perfect trade”
- do not recommend live execution while live execution is locked
- keep it paper-only / decision-support language

7. Loading state cleanup
Make sure:
- THINKING does not stay stuck
- scanner failure clears loading
- text input stays usable
- quick suggestions stay usable
- voice does not break text chat
