Update ARX governance so users with their own connected MT5 bridge can define their own trading governance and are not restricted by ARX operator/shared-bridge limits.

This is a governance-scope separation task.

The product rule:

1. Users trading through their own personal MT5 bridge are trading their own broker account and their own capital.
   They should be allowed to set their own trading governance rules.
   ARX should not impose operator/shared-bridge restrictions on them.

2. Users trading through the shared/master MT5 bridge are trading through the operator-controlled bridge.
   They must remain subject to admin approval, operator allocation, platform risk controls, shared-bridge caps, and admin governance.

Do not rebuild the app.
Do not replace MT5 bridge logic.
Do not replace execution routes.
Do not bypass authentication.
Do not bypass bridge ownership verification.
Do not bypass security handshake.
Do not bypass audit logging.
Do not bypass idempotency / duplicate command protection.
Do not allow one user to trade another user’s bridge.
Do not weaken shared/master bridge restrictions.
Do not remove admin controls from shared bridge users.

==================================================
PRIMARY GOAL
==================================================

Separate governance by bridge ownership:

- PERSONAL_BRIDGE governance
- SHARED_MASTER_BRIDGE governance

For PERSONAL_BRIDGE users:
Allow complete trading freedom based on their own settings.

For SHARED_MASTER_BRIDGE users:
Keep existing admin/operator restrictions.

==================================================
DEFINE BRIDGE GOVERNANCE MODES
==================================================

Create or verify a bridge governance resolver.

Suggested modes:

PERSONAL_BRIDGE_SELF_GOVERNED
SHARED_BRIDGE_OPERATOR_GOVERNED
NO_BRIDGE
UNKNOWN

A user is PERSONAL_BRIDGE_SELF_GOVERNED only when:

- the MT5 bridge belongs to that authenticated user
- the bridge is connected
- the bridge ownership is verified
- the bridge is not the shared/master/operator bridge
- the user is not trading from operator allocation
- the user is not using pooled/shared funds
- the user is not impersonating another bridge
- the bridge session is fresh enough for execution

A user is SHARED_BRIDGE_OPERATOR_GOVERNED when:

- they trade through the centralized/master bridge
- they use operator allocation
- they use shared bridge execution
- admin approval is required
- admin caps apply

==================================================
PERSONAL BRIDGE USER FREEDOM
==================================================

For users on their own MT5 bridge, remove ARX-imposed trading restrictions such as:

- operator max lot cap
- operator daily trade count cap
- operator daily loss cap
- operator weekly loss cap
- operator allowed-symbol list
- operator max open positions
- operator forced stop-loss requirement
- shared bridge allocation cap
- admin approval requirement for live trading
- admin toggle requirement for trade access
- shared bridge risk profile
- shared bridge live execution prerequisites that only exist to protect operator funds

These users should be able to set their own rules:

- max lot size
- max open positions
- daily loss limit
- weekly loss limit
- allowed symbols
- require stop loss yes/no
- max trades per day
- scalping allowed yes/no
- news trading allowed yes/no
- AI assist allowed yes/no
- AI auto allowed yes/no if available for personal bridge
- one-click trading allowed yes/no
- confirmation required yes/no
- personal kill switch settings

If they set no personal limits, ARX should not invent operator-style limits for them.

UI language:
“You are trading through your own MT5 bridge. Your trading rules are self-governed.”

==================================================
NON-NEGOTIABLE PLATFORM SAFETY THAT STILL REMAINS
==================================================

These are not trading restrictions. They protect app integrity.

Always keep:

1. Authentication
User must be logged in.

2. Bridge ownership check
User can only trade through their own bridge unless admin/operator shared bridge access is explicitly granted.

3. Bridge freshness
Do not send commands to a stale/disconnected bridge.

4. Symbol mapping
Do not send a command if the symbol cannot be resolved to the connected MT5 broker symbol.

5. Idempotency
Prevent duplicate orders from double taps, retries, stream reconnects, or repeated command submissions.

6. Replay protection
Do not allow old commands to be resent.

7. Command integrity
Command payload must not change after approval/dispatch.

8. Audit logging
Every live command must be auditable.

9. Result mapping
Broker fill/reject must map back to ARX command truth.

10. Security Handshake
Protect identity, permissions, bridge ownership, route safety, and command integrity.

11. User consent / personal settings
If the user enables one-click or AI auto for their own bridge, store that preference clearly.

12. No cross-user access
A user cannot read, control, or trade another user’s bridge/account.

13. No fake fills
Never mark filled without broker-confirmed result.

14. Emergency app integrity stop
If ARX detects command duplication, route corruption, spoofed bridge, or account mismatch, block execution.

Do not remove these.

==================================================
RISK GOVERNOR BEHAVIOR BY GOVERNANCE MODE
==================================================

Update Risk Governor so it behaves differently by bridge governance mode.

For SHARED_BRIDGE_OPERATOR_GOVERNED:
Risk Governor enforces:
- admin allocation
- max lot
- allowed symbols
- daily/weekly loss caps
- open position caps
- required stop-loss if configured
- operator kill switch
- user approval toggle
- shared bridge limits
- admin restrictions

For PERSONAL_BRIDGE_SELF_GOVERNED:
Risk Governor should become a personal governance interpreter, not an operator limiter.

It should enforce only:
- the user’s own configured rules
- bridge ownership
- bridge health/freshness
- symbol resolution
- command integrity
- security requirements
- platform safety requirements

If user has no personal rule configured:
- do not block for missing operator limits
- do not apply shared bridge restrictions
- do not force stop loss
- do not force max lot beyond broker/app technical validation
- do not force allowed symbol list beyond what the connected broker supports

Risk message for personal bridge:
“Allowed by your personal MT5 bridge governance.”

Risk message for shared bridge:
“Checked against shared bridge governance.”

==================================================
AACI BEHAVIOR BY GOVERNANCE MODE
==================================================

AACI should understand governance mode.

For personal bridge:
AACI checks system cohesion:
- bridge connected
- symbol mapped
- account snapshot available if needed
- command route ready
- security handshake passed
- audit ready
- duplicate/replay protection active
- chart/scanner truth if action depends on chart/scanner
- user personal rules if configured

AACI should not block because admin shared-bridge approval is missing.

For shared bridge:
AACI keeps current admin/operator checks.

Add AACI field:
governanceMode:
- PERSONAL_BRIDGE_SELF_GOVERNED
- SHARED_BRIDGE_OPERATOR_GOVERNED
- NO_BRIDGE
- UNKNOWN

==================================================
SECURITY HANDSHAKE BEHAVIOR
==================================================

Security Handshake must remain mandatory.

For personal bridge, it verifies:
- authenticated user
- owns bridge
- bridge token/session valid
- bridge belongs to user
- command is fresh
- idempotency key valid
- no replay
- route is allowed
- audit writable
- no account/bridge mismatch

It must not enforce shared-bridge admin approval when governanceMode is PERSONAL_BRIDGE_SELF_GOVERNED.

Ruby can still warn:

- “blocked by your personal rule”
- “blocked by platform safety”
- “blocked by shared bridge governance”
