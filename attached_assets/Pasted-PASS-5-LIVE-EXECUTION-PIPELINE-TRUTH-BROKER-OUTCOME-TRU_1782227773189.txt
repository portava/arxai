Audit scope:

A) Inventory every live order entry point.
Find and map all paths that can initiate, close, modify, reverse, or manage real/live trades, including but not limited to:
- Scanner chart trade controls.
- Trade page/manual ticket.
- One-click trade.
- Shared/live trader ticket.
- Admin/master allocation trade paths.
- Emergency close paths.
- Live test cycle paths.
- Ruby/Eleanor-assisted trade suggestion paths, if any can execute or prefill executable tickets.
- Any route under /api/trades/*, /api/me/live/*, /api/me/one-click/*, /api/live/*, /api/admin/*, or similar.
- Any direct MT5/bridge call path.

For each entry point, identify:
- Frontend component/hook/service.
- API route.
- Backend service.
- Final live dispatch function.
- Whether it can reach real broker execution.
- Whether it is live, demo, paper, or shared-live scoped.

B) Prove the execution chokepoint.
Directly verify whether all real live execution converges through the same protected live dispatch path, especially dispatchLiveCommand if that remains the true chokepoint.

Confirm whether every live path enforces or calls into the same protection stack before any real broker command:
- Emergency stop.
- Account mode checks.
- Live/demo/paper/shared-live routing.
- Bridge connected/heartbeat freshness.
- Trader approval.
- Full activation toggle/approval state.
- Broker account attachment.
- Risk sizing.
- Max loss / daily loss.
- Margin/equity/balance checks.
- Symbol permission/session restrictions.
- News/volatility restrictions if implemented.
- Duplicate command/idempotency controls if implemented.
- Any kill-switch or circuit breaker.

If any path bypasses the chokepoint or calls the bridge/MT5 directly, classify risk clearly.

C) Broker outcome truth.
Prove how the app decides that a live order succeeded, failed, is pending, partially completed, or timed out.

Verify for:
- OPEN / BUY / SELL.
- CLOSE.
- CLOSE_ALL.
- Partial close.
- MODIFY_SL_TP.
- Break-even.
- Reverse, including both legs.
- Pending order cancel.
- Live-shared trade execution.

Confirm:
- UI success only appears after a real MT5/bridge result.
- A real broker ticket or confirmed broker close is required for terminal success.
- Rejections show real retcode/message where available.
- Timeouts do not become fake fills.
- Pending commands stay visibly pending or resolve honestly.
- Partial failures are not collapsed into fake success.
- Reverse action does not claim full success if close succeeds but reopen fails.
- The system does not permanently persist an optimistic fill without broker proof.
- Any optimistic UI state rolls back or remains pending honestly.

D) Trade history and open-position truth.
Trace the truth source for:
- Open positions.
- Closed trades.
- Trade history.
- Floating P/L.
- Balance.
- Equity.
- Margin/free margin.
- Investor allocation views affected by open trades.
- Admin/master/manual exposure views.

Confirm:
- Open trades come from real bridge/MT5/live position state or are clearly labeled if locally derived.
- Closed trades disappear promptly from open positions.
- History is reconciled after reconnect.
- Duplicate trade rows are prevented or flagged.
- Externally closed trades are detected.
- Auto-refresh/manual refresh uses honest wording and does not claim a broker sync if it only refreshes local state.
- Investor and admin views do not mix finalized withdrawable values with indicative/open P/L unless explicitly labeled.

E) Failure and reconnect behavior.
Inspect code paths for:
- MT5 disconnect mid-order.
- Stale heartbeat before order.
- Broker timeout.
- Delayed fill after timeout.
- Duplicate click / duplicate command retry.
- Network error after command dispatch.
- Pending command stuck.
- Bridge reconnect after a trade closed externally.
- User refresh while command pending.
- Auto-refresh while bridge stale.
- CLOSE_ALL partial failures.
- Emergency stop triggered while commands are pending.

For each, state whether behavior is:
- Safe and truthful.
- Safe but confusing.
- Unsafe.
- Unknown / insufficient proof.

F) Admin/live-shared truth.
Verify:
- Admin/master/live-shared actions are scoped separately from normal users.
- Normal users cannot access admin/master-only trade controls.
- Live-shared/manual/master rows do not leak into normal user charts or position lists.
- Live-shared trades do not create false ownership.
- User-facing balances, payable values, and withdrawable values do not falsely include master/manual exposure unless intentionally and clearly labeled.
- Admin allocation screens separate finalized truth from indicative open-trade estimates.

G) Privacy and permissions.
For all live execution and position/history routes, verify:
- Auth is required.
- User ID scoping is enforced on reads and writes.
- Role-gated routes are protected.
- Admin routes are actually admin-only.
- Shared-live visibility is intentionally mode-gated.
- Users cannot submit another user’s ID/account ID to trade or view positions unless explicitly authorized and role-gated.
