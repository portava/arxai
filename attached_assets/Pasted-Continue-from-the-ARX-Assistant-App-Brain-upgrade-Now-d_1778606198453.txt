Continue from the ARX Assistant / App Brain upgrade.

Now do a full proof, QA, and runtime validation pass so we know the assistant truly understands the app and the floating UI is actually fixed in the live app.

Main objective:
The ARX Assistant should be able to answer app-wide questions from any page, using real app state when available, and it must never show “No help topics for this page yet.”

Phase 1 — Verify actual assistant behavior
1. Run the app locally.
2. Open the live UI in mobile width and desktop width.
3. Confirm which assistant component is actually rendering.
4. Confirm the old stuck/pinned help behavior is gone.
5. Confirm the expanded assistant panel does not block:
   - bottom nav
   - More button
   - Help Center chips
   - Emergency Stop
   - menu/sidebar
   - page buttons

If it still blocks anything, fix the actual rendered CSS/component before continuing.

Phase 2 — Connect assistant to real app status
The assistant should not only use static help text. It should read current app state where possible.

Wire these real statuses into the assistant context:
- current route/path
- current page title
- user role from secure server/auth context
- paper only status
- live trading disabled status
- live broker execution disabled status
- MT5 deferred / simulator mode status
- sim engine status
- selected symbol, such as FX:EURUSD
- intents count
- broker connection status
- heartbeat status, if available
- readiness status, if available
- emergency stop status, if available

Important:
Do not hardcode these statuses if existing state/store/API values already exist. Reuse the app’s real state sources.

Phase 4 — Route coverage validation
Create a route knowledge coverage validator.

It should scan all visible routes from App.tsx and confirm each route has:
- title

- safety notes

Report:
- total routes found

Phase 6 — Add in-app assistant diagnostics
Add an internal/dev-only diagnostic panel or console output that shows:
- assistant mode: local deterministic or OpenAI/API grounded mode
- current route context
- current status context
- matched knowledge source
- confidence level
- fallback level used
- missing knowledge logs

Only show this to tester/admin/owner roles. Do not expose secrets or API keys.

Phase 7 — Fix fallback behavior
Assistant fallback must follow this order:
1. current page knowledge
2. route-related knowledge
3. status/badge knowledge
4. global ARX app knowledge
5. safe fallback with missing-knowledge logging

The user should always receive a useful answer, even if the exact page has no custom topic yet.

Replace “No help topics for this page yet” with something like:
“I don’t have a page-specific note for this exact area yet, but here’s what I know from the ARX app system…”
