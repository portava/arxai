Run a dedicated AI Bot / Eleanor Performance Truth Audit for ARX AI.

Goal:
Make sure the AI bot, Eleanor, can actually perform based on ARX’s real app intelligence — not isolated chat logic, not fake confidence, not local-only suggestions, and not disconnected “AI-sounding” responses.

Eleanor must be able to read and reason from the same central truth systems used by the rest of the app:
- scanner truth
- chart action truth
- selected symbol/timeframe
- market data freshness
- MT5 bridge state
- live account state
- open positions
- closed trades/history
- Profit Mission state
- Auto Pilot state
- risk/governance settings
- one-click state
- kill switch
- admin/user live approval
- notifications/audit events
- strategy registry/config
- FVG/flame/trend logic where available

Do not rebuild Eleanor. First inspect what is actually built, then patch only confirmed gaps. No fake validation.

Core rules:
- Eleanor must not claim she can see something unless backend/app truth proves it.
- Eleanor must not say a trade was placed unless the live pipeline confirms it.
- Eleanor must not bypass live execution gates.
- Eleanor must not invent account balance, P&L, bridge state, scanner verdicts, candle data, or open positions.
- Eleanor must not give fake confidence scores.
- Eleanor must not pretend Auto Pilot or Profit Mission is active unless backend truth says so.
- Eleanor must route any live trade request through the same existing instant-trade / live intent / 18-gate execution pipeline used by the rest of ARX.
- If Eleanor cannot access a data source, she must say it is unavailable instead of guessing.
- If voice or chat is only advisory, label it honestly.
- If a requested action is blocked, Eleanor must explain the exact blocked reason.

Audit scope:
1. Eleanor chat UI
2. Voice / speech controls
3. Chat command parser
4. AI planner / decision engine
5. Scanner-to-Eleanor context
6. Chart-to-Eleanor context
7. Auto Pilot-to-Eleanor context

14. Notification/audit event context

17. Any API routes used by Eleanor

Part A — Identify the real central intelligence system

Find and document:
- The actual AI planner/brain module(s)
- The chat API route(s)
- The execution intent parser
- The scanner verdict source
- The chart action source
- The Auto Pilot planner source
- The Profit Mission context source
- The voice transcript/action path
- The audit/event logging path

Classify Eleanor’s current intelligence connection:
- REAL: reads central app truth and can act through proper backend paths
- PARTIAL: reads some truth but misses key systems
- SHELL: mostly UI/chat without real app context
- MISLEADING: claims app awareness/action without backend truth
- HIDDEN: backend intelligence exists but UI cannot call it
- DUPLICATE: separate AI logic exists outside central brain and may conflict

Part D — Execution safety audit for Eleanor

For every Eleanor path that can place/close/modify a trade:
- Trace UI command → API route → service → live queue / 18-gate pipeline.
- Verify it does not import direct MT5/broker mailbox writer.
- Verify it cannot call backtest/testing routes for live trading.
- Verify mission/autopilot/chat execution paths are separate but converge only at the approved live pipeline.
- Verify kill switch blocks it.
- Verify bridge stale/offline blocks it.
- Verify missing approval blocks it.
- Verify entitlement blocks it.
- Verify per-user/account isolation.
- Verify rejected result does not render as success.
- Verify one-click behavior matches current app contract.

Add/extend guards if missing:
- Eleanor/chat cannot import direct broker/MT5 writer.
- Eleanor/chat live actions must route through approved execution service.
- Eleanor/chat cannot call backtest/testing live paths.
- Eleanor/chat cannot use Math.random/fake P&L/fake scanner verdicts in user-facing output.
- Eleanor execution responses must include backend accepted/rejected/blocked truth.
