Run a full ARX AI app-wide wiring audit, repair, and end-to-end cooperation check.

The goal is to make sure the entire app and entire AI ecosystem are actually connected across all layers, functions, pages, agents, services, routes, UI surfaces, backend logic, admin controls, scanner, Ruby, risk system, scalp engine, governance, lifecycle, live execution readiness, and MT5/Deriv bridge systems.

The premise of ARX AI only works if every part of the system cooperates with the rest of the system. Do not leave isolated modules, decorative agents, fake traces, unused services, disconnected UI buttons, orphaned functions, duplicated logic, or features that exist in code but do not affect real app behavior.

Do not rebuild the app. Do not remove working features. Do not redesign the UI. This is a full wiring, integration, repair, and proof pass.

Search every file, every function, every route, every service, every agent, every scanner path, every Ruby path, every admin path, every trade path, every risk path, every lifecycle/governance path, and every UI action.

Fix anything incorrectly wired. Wire anything not yet wired. Remove or flag anything that is dead, duplicated, fake, unsafe, or misleading.

PHASE 2 — APP-WIDE WIRING MAP

Build and verify the full cooperation map between systems:

1. Ruby
    Ruby must be connected to:

* Scanner signals
* selected market explanations
* agent scoring/lifecycle
* governance outcomes
* risk analysis
* reward-to-risk analysis
* stop loss/take profit reasoning
* scalp/flame analysis
* market history
* market news/current events where available
* user role/permissions
* saved chats/memory
* admin-safe vs user-safe explanation modes

Ruby must explain things in plain English and never expose backend function names, raw schema names, route names, environment variable names, or developer-only wording to normal users.

2. Scanner
    Scanner must be connected to:

* Focus Scan
* Broad Scan
* Flame Scalp
* selected market explanation
* Ruby reasoning
* agent scores
* governance decisions
* risk downgrades
* reward-to-risk logic
* news/current-event caution
* market history/backtest context where available
* user-facing ranking
* admin trace

Scanner rankings must actually change when agent confidence, risk score, governance outcome, or scalp/flame quality changes.

3. Flame Scalp Engine
    Flame Scalp must be connected to:

* scanner results
* Focus path
* Broad path
* Builder path
* Ruby explanations
* risk engine
* reward-to-risk
* candle momentum logic
* multi-trade scalp logic
* entry/exit management
* stop loss/take profit reasoning
* agent lifecycle/scoring
* governance challenges
* admin trace

Confirm flame/scalp logic is not just detecting fast candles. It must evaluate strength, continuation, exhaustion, choppiness, late entry risk, reversal risk, wick rejection, spread/slippage concern, and whether the move has a true running flame.

4. Risk Engine
    Risk must be connected to:

* scanner ranking
* Ruby explanation
* trade ticket
* one-click scalping
* SL/TP editor
* reward-to-risk
* agent governance
* agent lifecycle
* account protection
* exposure checks
* active positions
* pending orders
* admin visibility

Risk AI must be able to downgrade or caution weak setups. It should not be decorative.

5. Reward-to-Risk / SL / TP Logic
    Reward-to-risk must be connected to:

* scanner
* Ruby
* trade ticket
* recommended stop loss
* recommended take profit
* market structure
* broker spread/bleed consideration
* risk warning
* scalp engine
* active trade modification
* admin trace when needed

Users should be able to enter and edit SL/TP where intended. Recommended SL/TP should make sense based on the market assessment and not sit unrealistically at entry where broker bleed/spread could cause bad execution.

6. AI Agent Scoring & Lifecycle
    Agent scoring/lifecycle must be connected to:

* Ruby
* Scanner
* Flame Scalp
* Risk
* Governance
* Admin trace
* Learning Camp
* agent demotion
* agent promotion
* agent muting
* Traffic Controller
* Agent Factory

Weak agents should lose influence. Strong agents should gain influence. Agents in shadow or Learning Camp should not influence real recommendations as if they are active.

7. Governance Court
    Governance must be connected to:

* agent challenges
* scanner ranking changes
* Ruby explanation changes
* risk warnings
* scalp/flame confidence
* agent lifecycle changes
* admin trace
* Traffic Controller
* Agent Factory

Governance must produce actual outcomes such as approved, approved with caution, downgraded, rejected, escalated, needs more data, muted due to low confidence, delayed for speed, or Learning Camp review required.

8. Traffic Controller
    Traffic Controller must be connected to:

* Ruby requests
* scanner runs
* scalp/flame scans
* governance reviews
* agent participation
* speed protection
* admin trace

Do not call every agent for every action. Only call agents that are needed for the workflow. Slow or unnecessary agents should step back.

9. Agent Factory
    Agent Factory must be connected to:

* governance
* lifecycle
* admin visibility
* missing-task detection
* validation requirements
* shadow/advisory activation only

Do not allow uncontrolled self-replication. New agent proposals must require purpose, permissions, inputs, outputs, failure rules, scorecard, testing, and admin visibility.

10. Admin / OWNER
    Admin must be connected to:

* user management
* invite codes
* role permissions
* live trading permissions
* investor permissions
* owner live test cycle
* live broker execution status
* MT5/Deriv bridge status
* EA download link
* kill switches
* execution logs
* agent scoring
* governance trace
* Learning Camp
* Agent Factory
* QA reports
* environment/system status where appropriate

Admin/OWNER should have visibility and control. Normal users should not.

11. Trader User
    Trader user must be connected only to user-safe surfaces:

* Dashboard
* Markets
* Trade
* Ruby
* Risk
* Settings

Trader users should not see admin controls, backend logs, raw execution variables, internal agent details, system secrets, owner-only test panels, or developer wording.

12. Investor/View-Only User
    Investor/view-only users must only see investor-safe areas:

* funds
* allocation preference
* performance/reporting
* view-only activity
* settings

Investor users must not be able to place trades, access trader controls, access admin controls, or modify system execution.

13. Live Execution / MT5 / Deriv Bridge
    Audit the live execution path without accidentally disabling it or changing authorized live settings.

Confirm:

* bridge status is accurately displayed
* live execution controls are role-gated
* owner/admin permissions are respected
* order queue path is connected
* result mapping is connected
* fills/close fills are reflected correctly
* P/L mapping is correct
* active positions update correctly
* pending orders update correctly
* close/modify actions connect correctly
* logs are visible to admin
* errors explain the real block reason
* no fake “success” appears if broker did not accept or fill the order

Do not silently turn live trading off. Do not add demo-only restrictions. Do not break existing live testing configuration. If live execution is blocked by a real missing connection, report the exact blocker and fix it if it is in-app wiring.
