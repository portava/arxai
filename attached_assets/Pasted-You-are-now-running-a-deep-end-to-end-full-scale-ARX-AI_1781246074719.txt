PHASE 3 — TRUTH CONTRACTS

Every test must use a truth contract. Do not mark anything passed because it visually appears okay.

Create a Truth Contract table with:

- Function/Feature
- Source of Truth
- Expected Result
- Actual Result
- Evidence
- Pass/Fail
- Severity
- Fix Needed

Use these truth sources:

1. Live Account/Dashboard Truth
Source of truth:
- MT5 bridge account snapshot
- balance
- equity
- margin
- free margin
- margin level
- floating P/L
- open position count

Pass condition:
Dashboard must match normalized MT5 account snapshot within a small tolerance. It must not show cached/fake/stale P/L as live.

2. Open Trades Truth
Source of truth:
- MT5 open positions
- backend normalized live position snapshot

Pass condition:
Every live MT5 position must appear in UI with correct symbol, direction, lot, entry, SL, TP, current price, floating P/L, and status. Closed positions must disappear from Open Trades and move to history if history exists.

3. Scanner Truth
Source of truth:
- selected symbol
- feed availability
- candle freshness
- quote freshness
- scanner calculation inputs

Pass condition:
Scanner must not rank or recommend a market using missing, stale, or mismatched data without clearly labeling it. Scanner results must match the selected market and must not fabricate confidence.

4. Chart Truth
Source of truth:
- candle source
- quote source
- feed freshness timestamp
- selected symbol

Pass condition:
Chart must render only valid candles for the selected symbol. If feed is unavailable/stale/mismatched, show honest unavailable/stale state. Do not show composite or stale candles as live.

5. Ruby Truth
Source of truth:
- selected symbol
- current quote/candles
- indicators/market structure
- account/risk settings where relevant
- news/events if available
- trade state

Pass condition:
Ruby must analyze the correct market, use available current data, disclose stale/unavailable data, explain entry/SL/TP/risk/reward/confidence, and never expose backend function names or developer terms to normal users.

6. Live Trade Truth
Source of truth:
- backend order request
- risk/governance decision
- MT5 command queue
- EA/broker execution result
- resulting MT5 position or rejection

Pass condition:
A live trade test only passes if the trade request reaches the correct execution path, receives a real EA/broker result, maps the result correctly, and UI/dashboard/open trades update from the actual MT5 truth state. A 200 response alone is not a pass.

7. Admin/User Permission Truth
Source of truth:
- authenticated user role
- backend role enforcement
- UI visibility rules

Pass condition:
Admin-only features must be hidden from regular users and blocked by backend if accessed directly. User/admin toggle must actually change the visible scope and backend permission behavior.

8. Speed Truth
Source of truth:
- measured timestamps
- frontend performance marks
- backend logs
- network timings

Pass condition:
Critical trading actions must acknowledge instantly and complete within measurable thresholds. Record exact durations.

Suggested thresholds:
- UI response to button click: under 250ms
- backend order request accepted: under 1 second if bridge healthy
- dashboard/open trades refresh after MT5 change: under 1–3 seconds
- scanner symbol switch visible response: under 500ms
- chart first render: under 1.5 seconds when feed available
- Ruby typing indicator: under 150ms
- Ruby first response activity: under 1 second when possible

PHASE 5 — FIXING RULES

After the audit identifies failures, fix them carefully.

Rules:
1. Preserve working wiring.
2. Do not remove features unless clearly dead, duplicate, or unused and documented.
3. Do not redesign the whole app during audit unless required to fix broken behavior.
4. Do not expose backend/internal wording to users.
5. Do not fake pass anything.
6. Do not use frontend-only success for backend-critical actions.
7. Do not mark live trade passed unless MT5/EA/broker result confirms it.
8. Fix the root cause, not the symptom.
9. After each fix, rerun the failed test and connected ecosystem tests.
10. If a fix risks breaking another system, choose a safer adapter/wrapper approach instead.
