BUILD PHASE — Audit Log Center + Compliance Evidence Export

Use the current codebase. Do not rebuild unrelated systems.

Goal:
Create an admin-only Audit Log Center where the operator can review safety events, trade lifecycle events, admin actions, Ruby actions, voice actions, bridge events, queue events, kill switch actions, reconciliation actions, user approvals, and blocked trade decisions. Add safe evidence exports for internal review, troubleshooting, and compliance-support documentation.

Important:
Check what already exists first. Reuse the current audit log model, admin dashboard, liveCommandPipeline, trade queue, bridge masking, reconciliation center, kill switches, user approval system, risk gate, Ruby logs, and auth/session system. Do not create a duplicate logging system.

This is an internal evidence/export system. Do not claim legal, broker-dealer, regulatory, tax, or financial compliance certification unless that framework is separately implemented and reviewed.

4. Audit event structure
Each audit event should safely store:
- eventId
- timestamp
- eventType
- severity
- actorUserId
- actorRole if safe
- targetUserId if applicable
- accountMode
- entityType
- entityId
- commandId if applicable
- positionId if applicable
- reservationId if applicable
- bridgeId if applicable
- sharedMasterAccountId if applicable
- symbol if applicable
- source page/action
- result: success / blocked / failed / needs_review / ignored
- user-facing reason
- internal safe reason
- before/after state summary when safe
- evidence references
- request/session metadata if safe
- masked payload summary only

Never store or show:
- bridge tokens
- API keys
- session secrets
- token hashes
- account passwords
- raw account credentials
- raw sensitive bridge payloads
- raw audio
- full private prompt payloads
- other-user data to normal users
