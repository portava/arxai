BUILD PHASE — Ruby Full App Knowledge + User-Specific Help Brain

Use the current codebase. Do not rebuild unrelated systems.

Goal:
Upgrade Ruby so she can answer questions about the entire ARX AI app, explain every feature, understand the current user’s account state, help troubleshoot trading/app issues, and give user-specific guidance without exposing admin-only data, other users, shared master totals, secrets, or fake information.

Ruby should feel like the user’s private ARX AI assistant.

1. Inspect existing Ruby/AI system first
- Inspect current Ruby chat UI, AI routes, prompt builder, memory system, trading context tools, scanner context, chart context, account shell, onboarding status, notifications, admin approval status, queue status, trade ledger, and app route/component structure.
- Reuse existing Ruby/chat infrastructure.
- Do not create a second disconnected AI system.
- Only add missing app-knowledge, user-context, routing, memory, and safety pieces.

Ruby should be able to answer:

- “Why is EURUSD moving?”

- “Where should I place TP?”

6. Status-aware responses
Ruby should check the actual user/account/trade state before answering.

Examples:
- If user has no trades: “You don’t have any open trades yet.”
- If onboarding incomplete: “Finish account setup first.”
- If shared master pending: “You’re waiting for admin approval.”
- If allocation missing: “Your allocation has not been assigned yet.”
- If bridge disconnected: “The bridge is not connected right now.”
- If trade blocked: explain the actual safety gate reason.
- If command queued: explain the queue status.
- If trade filled: explain the mapped position.
- If no scanner symbol selected: prompt user to choose a symbol.

Ruby should not give generic answers when real state is available.

7. Private memory
Ruby should maintain user-specific saved chats and memory unless the user clears it.

Add or verify:
- memory is scoped by authenticated userId
- memory is not shared across users
- memory is separated from admin/global data
- user can clear Ruby memory
- Ruby does not remember fake first-load data
- logout/login switch does not leak previous user chat context
- Ruby can summarize the current user’s previous conversations only when allowed

8. Navigation help

Ruby can say:
- “Go to My Scanner and choose a symbol.”
- “Open My Trades, then select the position.”
- “Your account setup is under My Account.”
- “Admin approval is required before shared live trading.”
- “Your one-click toggle is off right now.”

If deep links/routes exist, connect Ruby replies to safe route names/buttons.

9. Action suggestions
Ruby should suggest safe next actions based on state.

Examples:
- “Start in demo mode.”
- “Finish onboarding.”
- “Request shared master access.”
- “Wait for admin approval.”
- “Choose a symbol to scan.”
- “Open a trade ticket, but review risk first.”
- “Refresh bridge status.”
- “Ask admin to assign allocation.”
- “Review why this trade was blocked.”

Ruby should not execute trades, close trades, change SL/TP, enable one-click, or switch live mode without explicit user action and existing safety gates.

10. Admin-safe behavior
Normal users must not be able to ask Ruby for:
- other user data
- shared master global balance
- admin approval console data
- bridge secrets
- API keys
- session secrets
- account credentials
- token hashes
- raw server logs
- private audit logs
- all-user trade queue data

If a normal user asks, Ruby should respond with a clean boundary:
“I can only show your private account, trades, risk, and performance.”

Admins may ask Ruby admin-level questions only on admin routes or admin-authenticated context.

11. Ruby and admin mode
For admin users only, Ruby can explain:
- bridge health
- queue health
- shared master mapping status
- pending user approvals
- needs-review items
- per-user allocation summaries
- why a user is blocked from live trading
- admin next steps

Even for admins, Ruby must not expose secrets.

12. Error/troubleshooting brain
Ruby should explain app errors in user-facing language:
- no raw stack traces
- no backend code dumps
- no secret exposure
- no scary technical language unless expanded by user
- clear next step
- route/action to fix if available

Examples:
- “Your trade was blocked because your account is waiting for approval.”
- “The bridge heartbeat has not updated yet.”
- “This symbol is not enabled for your account.”
- “Your daily loss limit has been reached.”
- “This command needs admin review before it can continue.”
