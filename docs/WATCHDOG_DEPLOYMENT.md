# Deploying the Independent Protection Watchdog (#28)

The watchdog process has existed since the resilience front
(`artifacts/api-server/src/watchdog.ts`). What did **not** exist was a way to
actually run it anywhere: `docs/WATCHDOG.md` told you to run `pnpm run
watchdog`, and no such script existed in the root `package.json`. It also had
no way to reach the owner (a bare optional webhook), and no way for anyone to
tell whether the watchdog itself was still alive.

This document is the runnable package: the command, the environment, the
liveness surface, and — honestly — what each deployment topology does and does
not protect against.

---

## 1. The command

One command, every topology. What changes is the environment and the box.

```bash
pnpm run watchdog          # loop mode
pnpm run watchdog:once     # a single pass; the exit code carries the verdict
```

Both call `scripts/watchdog/start-watchdog.sh`, which **refuses to start
silently misconfigured**. A watchdog that runs but reaches nobody is worse than
no watchdog, because the dashboard looks covered.

| Exit code (`--once`) | Meaning |
|---|---|
| `0` | Every section was readable, no CRITICAL condition. |
| `1` | Read everything, found a CRITICAL condition. |
| `2` | **Could not verify** — database unreachable, or no `DATABASE_URL`. Never treat this as a pass. |

Those codes make topology (c) below alertable from any scheduler.

## 2. The minimal environment

| Variable | Required | Meaning |
|---|---|---|
| `ARX_WATCHDOG_DATABASE_URL` | yes (or `DATABASE_URL`) | The watchdog's **own** connection. Prefer a dedicated read-only role — see §6. The session additionally forces `SET default_transaction_read_only = on`, so Postgres itself refuses writes even on a read-write URL. |
| `ARX_WATCHDOG_ALERT_INGEST_URL` | to reach the owner | Full URL of the app ingest, e.g. `https://<app-host>/api/watchdog/alerts`. |
| `ARX_WATCHDOG_INGEST_TOKEN` | to reach the owner | Shared secret, ≥16 chars, presented as `Authorization: Bearer …`. **The same value must be set on the API server.** Owner-chosen (see §7). |
| `ARX_WATCHDOG_WEBHOOK_URL` | strongly recommended | An **independent** operator channel (Slack/ntfy/PagerDuty). This is the only leg that still works when the app itself is the thing that is down. |
| `ARX_WATCHDOG_TOPOLOGY` | recommended | `same_host` \| `second_repl` \| `external_host`. Self-reported; recorded on the heartbeat so the operator can see which failure domain is actually covered. |
| `ARX_WATCHDOG_INSTANCE_ID` | optional | Defaults to `<hostname>:<pid>`. Set it when running more than one instance. |
| `ARX_WATCHDOG_INTERVAL_MS` | optional | Loop interval; default 60000, floor 5000. |
| `ARX_WATCHDOG_HEALTH_PORT` / `_HOST` | optional | Liveness port; default `8091` on **`127.0.0.1`** (loopback). `/healthz` is **unauthenticated** — see the warning in §3 before widening the bind. |
| `ARX_WATCHDOG_ALLOW_UNARMED` | optional | `1` to run logs-only **on purpose**. Without it the start script refuses when the alert path is disarmed. |

No value above is generated by this repository. Every secret is the owner's to
choose and to set.

## 3. Its own liveness

Loop mode binds a small HTTP server:

| Path | Answers |
|---|---|
| `GET /healthz` | **200** only when the last pass was fresh **and actually read everything**. `503` for `never_ran`, `stale`, and `cannot_verify`. Body always carries a plain-language `reason`. |
| `GET /livez` | `200` whenever the process is running. Process liveness **only** — it says so in the body, so it can never be mistaken for "protection is verified". |

Point an uptime monitor at `/healthz`, not `/livez`.

> **This port has no authentication.** It binds `127.0.0.1` by default, and it
> must stay that way unless you have a reason. Its full body lists the scoped
> finding keys — `unprotected_position:9002` — plus the instance id (which
> defaults to `<hostname>:<pid>`) and the topology. On a VPS with a firewall
> hole, or on a Repl with the port exposed, that tells an anonymous caller
> exactly **which** positions are unprotected and **whether protection is
> currently unverifiable**. That is an attacker's shopping list.
>
> If you need an external monitor to reach it, you have three options, best
> first:
>
> 1. probe locally (`curl 127.0.0.1:8091/healthz`) and have your agent report out;
> 2. put the port behind your own reverse proxy with auth or an IP allowlist;
> 3. set `ARX_WATCHDOG_HEALTH_HOST=0.0.0.0` and accept the **redacted** body.
>
> Option 3 is automatic and needs no extra flag: any non-loopback bind drops
> the body to counts only — no scoped keys, no instance id, no topology, and
> no `cannot_verify` driver message. `ok`, `status`, `reason` and the HTTP code
> are identical in both modes, so **an uptime monitor sees exactly the same
> signal either way**. The process logs `watchdog_health_port_publicly_bound`
> at startup whenever it is running in that mode, and the body itself carries
> `"detail": "redacted"` so nobody mistakes an empty `activeFindingKeys` for
> "no findings" (`activeFindingCount` carries the real number).

Separately, every pass POSTs to the app, which upserts a row in
`watchdog_heartbeats` (the app writes it; the watchdog cannot — its session is
read-only). `GET /api/admin/watchdog/status` shows those rows to an
ADMIN/OWNER. An empty list renders as **"no watchdog instance has ever reported
— protection is NOT being independently verified"**, not as a green tick.

## 4. The three topologies, honestly

The watchdog is a separate **process**. How separate its **failure domain** is
depends entirely on where you run it, and that is an owner infrastructure
decision, not a code decision.

### (a) `same_host` — second process beside the API server

Available immediately, zero infrastructure.

* **Protects against:** the api-server process crashing, wedging its event
  loop, being OOM-killed, or deadlocking — while positions are open. It sees
  the app stop writing health checks and audit events and alerts on it.
* **Does NOT protect against:** anything that takes the box. **A same-host
  watchdog dies with the box.** Host outage, Repl sleep/restart, network
  partition of the host, container eviction — the watchdog goes down at the
  same instant as the thing it was watching, and *nobody is told, because the
  process that would have told you is also dead*. Its silence looks exactly
  like calm.
* **Honest summary:** it upgrades "the app died silently" to "the app died and
  I was told". It does nothing for "the host died".

### (b) `second_repl` — a second Replit instance

* **Protects against:** everything in (a), **plus** total loss of the app's
  Repl — process, container and all. The watchdog is still up, still reading
  the database, and still able to POST and to page you.
* **Does NOT protect against:** a Replit-wide or region-wide outage that takes
  both instances; a database outage (it alerts `CANNOT_VERIFY`, which is the
  correct answer, but it cannot *see* protection state during one); and it
  cannot reach the app leg of the alert path while the app is down — this is
  exactly why `ARX_WATCHDOG_WEBHOOK_URL` matters, and why a degraded delivery
  is logged as `alert_delivery_degraded` rather than assumed to have worked.
* **Honest summary:** the sensible default for live capital on Replit.

### (c) `external_host` — any host outside Replit (VPS, laptop, cron, CI)

Two shapes:

* **Resident loop:** the same command under systemd/pm2/Docker with a restart
  policy, probing `/healthz`.
* **Scheduled `--once`:** cron / GitHub Actions running `pnpm run
  watchdog:once`, alerting on exit code `1` or `2`. Cheapest true off-host
  option.

* **Protects against:** everything in (b), plus a provider-wide Replit outage.
* **Does NOT protect against:** a database outage (still `CANNOT_VERIFY`); and
  in the scheduled shape, **anything that happens between runs** — a 15-minute
  cron means up to 15 minutes of an unprotected position going unnoticed. Say
  the interval out loud when you choose it.

### What none of them protect against

**Broker-venue failure.** If the venue itself loses or never accepted the
protective order, no watchdog on any host can stand in for it. Broker-side
SL/TP living at the venue is the only layer that survives every row above —
which is precisely why the watchdog's first check is that those orders exist.

Also: the watchdog **only observes**. It has no authority to close, modify,
place, or engage anything, by design (auto-close is `ALERT_ONLY` platform-wide,
CLAUDE.md §3). It shortens the time between a problem and a human knowing. It
never shortens the time between a problem and a fix.

## 5. The alert path

```
watchdog process ──POST /api/watchdog/alerts (Bearer)──▶ api-server
                                                          └─▶ createNotification()
                                                                └─▶ /api/me/notifications
                                                                    + NotificationCenter + bell
                                                                    + web push (VAPID, if configured)
   └── (independent) ──POST ARX_WATCHDOG_WEBHOOK_URL ──▶ operator channel
```

It lands in the product's **existing** notification service — the one the
Alert Preferences UI was repointed at — not a new silo. CRITICAL findings
bypass per-source preferences and quiet hours (that behaviour already exists in
`createNotification`), so an unprotected position reaches the owner at 3am.

Recipients are **operators only** (users whose product role resolves to ADMIN or
OWNER). The wire envelope strips `userId` and every secret-shaped key from the
evidence before it leaves the watchdog, and the ingest route re-strips on
receipt: an alert about one trader's position never carries that trader's
identity onto another account's screen.

Dedupe: `entityType = watchdog:<family>`, `entityId = <scope>`, 15-minute
bucket. Two unprotected positions are two alerts; the *same* unprotected
position for an hour is one alert with a repeat count.

**Delivery is never assumed.** `deliverAlert` returns a typed per-leg result;
anything other than `delivered` is logged as `alert_delivery_degraded` with the
reason and surfaced on `/healthz`. "We tried to tell you" is not "you were
told".

## 6. The read-only role (defence in depth)

Self-enforced read-only is real — Postgres refuses writes on the session — but
for topologies (b) and (c) the connection string leaves the app host, so a
dedicated role is worth the five minutes. The template is in
`docs/migrations-pending/hold-watchdog-deploy.sql`, deliberately commented out:
this repository's agents may not create or rotate a credential.

## 7. The owner presses

Everything above is built. These are the presses this agent did **not** make
and may not make:

1. **Choose and set `ARX_WATCHDOG_INGEST_TOKEN`** — the same value in the API
   server's environment and the watchdog's. Until then the ingest route returns
   `503 ingest_not_configured` and accepts nothing (fail-closed by design: an
   unauthenticated caller can inject neither a fake all-clear nor a fake
   CRITICAL).
2. **Apply `docs/migrations-pending/hold-watchdog-deploy.sql`** (creates
   `watchdog_heartbeats`; additive, `IF NOT EXISTS`).
3. **Choose the topology and provision the box** — for (b), a second Repl; for
   (c), a host or scheduler. Set `ARX_WATCHDOG_TOPOLOGY` accordingly.
4. **Set `ARX_WATCHDOG_ALERT_INGEST_URL`** to the deployed app's
   `/api/watchdog/alerts`.
5. **Set `ARX_WATCHDOG_WEBHOOK_URL`** to an operator channel that does not
   depend on the app being up.
6. *(optional, recommended for b/c)* **Create the `arx_watchdog_ro` role** with
   a password of the owner's choosing and point `ARX_WATCHDOG_DATABASE_URL` at
   it.
7. **Run the drill** — `docs/WATCHDOG_DRILL.md` — and confirm the alert
   actually arrives on the screen and the phone.

Until press 1 and press 4 are done, the watchdog runs and logs but **reaches
nobody**; it announces this at startup as `watchdog_alert_path_not_armed`, and
the start script refuses to launch unless you opt in with
`ARX_WATCHDOG_ALLOW_UNARMED=1`.
