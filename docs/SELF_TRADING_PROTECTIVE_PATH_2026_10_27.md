# Self-trading protective-action path — 27 October 2026

Branch `claude/self-trading-protective`, cut from the integration merge `444e726` (PR 99 head `11cb10a`). Trading, workers and settlement stay disabled. No broker, demo or network order test ran, no existing database was touched, no schema migration was added. Files owned by the MT5 team (`routes/mt5.ts`, `routes/mt5Live.ts`, `lib/mt5/*`, `mt5-bridge/*`) are read, cited and not edited.

This is offline evidence only. It does not establish real execution correctness or broker behaviour.

## 1. Owner decision and where each clause lives

> Retain the current stale-position restriction for now. Do not introduce a blanket bypass for protective actions. Implement a separate protective-action path that obtains fresh authoritative position evidence, verifies account and exact position identity, and guarantees the action cannot increase exposure, reverse the position or loosen its stop. If verification fails, hold the action and clearly explain why. Preserve manual controls and existing broker-side stops.

## 2. What "fresh authoritative evidence" means here

The server never asks the broker anything. Position facts arrive only when the EA pushes a complete positions sweep (`PushSnapshots()` every `SnapshotIntervalSeconds = 10` in `ARX_AI_Universal_Agent_v154.mq5:70, 212`; 5 s in older builds). The sweep writes `lastSyncedAt` **and** `lastReliableSnapshotAt` to the same instant and resets `brokerAbsentSnapshotCount` (`routes/mt5Live.ts:324-330`); a ticket missing from a complete sweep gets `brokerAbsentSnapshotCount + 1` (`mt5Live.ts:405-407`); afterwards the connection's `lastPositionsSnapshotAt` marker is stamped (`mt5Live.ts:433`). Reconcilers write `lastSyncedAt` alone (`liveCommandPipeline.ts:293, 522, 532, 610`), so `lastReliableSnapshotAt !== lastSyncedAt` identifies a row that the latest writer was not a sweep.

There is no pull. `POSITIONS_SNAPSHOT_REQUEST` is an allow-listed manual command (`routes/meMt5Commands.ts:18`); the v154 EA answers `GET_OPEN_POSITIONS` by posting a result JSON (`v154.mq5:560, 575`) that no server-side consumer writes into `arx_live_positions`. The path therefore *waits* for the next sweep rather than requesting one (section 12 lists the EA-side follow-up).

Evidence is accepted when all of the following hold (`evaluateProtectiveObservation`, rules in order, first failure wins):

1. `closedAt` and `reconcileState` are null (`PROTECTIVE_OBSERVATION_POSITION_CLOSED`).
2. `brokerAbsentSnapshotCount === 0` (`PROTECTIVE_POSITION_ABSENT_AT_BROKER`, terminal: the wait stops at once). Checked before the row's age and provenance because the sweep's absent bump stamps `lastReliableSnapshotAt` without touching `lastSyncedAt` (`mt5Live.ts:405-407`): a ticket already closed at the broker never has `lastSyncedAt` refreshed, so after 90 s it would always read as `_STALE` and, earlier, as `_NOT_FROM_SWEEP`; in either order the specific reason was unreachable and the wait polled its full budget every cycle (review finding F2; first seen as the PostgreSQL case "ticket went absent between draft and claim").
3. `lastSyncedAt` parses, is not future-dated and is at most 90 s old — the existing window, no new constant (`_TIMESTAMP_INVALID`, `_FUTURE_DATED`, `_STALE`).
4. `lastReliableSnapshotAt === lastSyncedAt` (`_NOT_FROM_SWEEP`).
5. Strictly newer than the hold (`mustBeAfterMs`), or, at the final claim, not older than the evidence the claim was taken on (`mustNotPrecedeMs`) (`_NOT_NEWER`). A non-finite bound refuses.
6. Newer than every command event on the ticket, including a manual close/modify sent during the wait (`_PREDATES_COMMAND`).
7. The bridge's `lastPositionsSnapshotAt` is present, not older than the row and within the 90 s window (`PROTECTIVE_SWEEP_MARKER_STALE`).
8. Heartbeat online, i.e. under 60 s (`heartbeatPolicy.ts:26, 103`) (`PROTECTIVE_BRIDGE_OFFLINE`). The stricter *fresh* bound (under 15 s, `heartbeatPolicy.ts:24, 95`) is applied separately just before the claim.
9. `currentPrice`, `entryPrice`, `volume` are finite and positive (`_PRICE_INVALID`).

Other close/modify commands on the ticket (`evaluateTicketCommands`, `freshFacts.ts:548`, pure): a command sent to the terminal that has neither `filledAt` nor `rejectedAt` and is not in a settled status (`LIVE_FILLED`, `_REJECTED`, `_FAILED`, `_BLOCKED`, `_CANCELLED`, `_CLOSED`, `_EXPIRED`; the Risk Governor's `LIVE_TERMINAL` list; a missing status is not settled) is *in flight* → `PROTECTIVE_HOLD_MANUAL_COMMAND_IN_FLIGHT`. A sweep newer than its send time does not prove the modify or close is reflected, so the path holds at once instead of waiting. With an evidence time (final claim), any event of any sent command at or after it, or a malformed event time, refuses `PROTECTIVE_TICKET_COMMAND_AFTER_EVIDENCE`.

## 3. Sequence (`runProtectiveActionPath`, `protectiveActionPath.ts:231`)

**Scheduling (review finding F1).** The manager's hold branch only queues a candidate (`queueProtectiveCandidate`, `livePositionManager.ts:494`) and continues with the next execution. `runAutonomousCycle` passes one cycle-scoped queue to every agent's `manageAgentPositions` and, after the per-agent loop has finished every ordinary evaluation, dispatch, reconciliation and ledger step, calls `drainProtectiveCycle` once (`autonomousCycle.ts:370-386`). The drain groups candidates by the entry's bridge, runs bridges concurrently and, within a bridge, runs candidates in queue order against one shared deadline, because one sweep refreshes every row on that bridge; no bridge waits past drain start + 20 s. A standalone `manageAgentPositions` call (tests; there is no other production caller) drains its own queue after its ordinary loop under the same bound (`livePositionManager.ts:616-622`). Candidates only exist for agents whose management was not paused (AACI); platform stop, arming and kill switch are re-read per candidate at drain time, and every gate runs again at dispatch.

No transaction and no row lock are taken anywhere in the path; the only write before dispatch is the compare-and-set on the execution's JSONB `managementState`. The whole body is wrapped in `try/catch`; any throw holds `PROTECTIVE_HOLD_INTERNAL_ERROR`.

1. **Classification, no IO.** Autonomy below L3 → `NOT_APPLICABLE`. The stale row is re-decided only to learn whether a protective trigger exists (`classifyProtectiveTrigger`: `INVALIDATION_BREACH → EXIT_INVALIDATION`, `BREAK_EVEN → MOVE_TO_BE`, `TRAIL → TIGHTEN_SL`; final/first target and HOLD are not protective → `NOT_PROTECTIVE`). That verdict is discarded; nothing from the stale row is acted on.
2. **Pre-checks that make waiting pointless.** Connection read + `verifyProtectiveBridge` (section 5, includes heartbeat online and `supportsManagementTargetV1`); `platformStop()` through `preCheckStopRefusal` (`PROTECTIVE_HOLD_PLATFORM_STOP_ENGAGED`; unreadable counts as engaged); user arming (`PROTECTIVE_HOLD_USER_NOT_ARMED`, `PROTECTIVE_HOLD_USER_KILL_SWITCH`). The entry-only self-trade kill switches are deliberately not read here.
3. **Wait budget.** `EXIT_INVALIDATION` gets `PROTECTIVE_EVIDENCE_WAIT_MS = 20_000` (two v154 sweep cadences); `MOVE_TO_BE` and `TIGHTEN_SL` get 0 and hold `PROTECTIVE_HOLD_DEFERRED_TO_NEXT_CYCLE` (INFO): stop tightening is not urgent and the ordinary path acts next cycle from a fresh row. The bridge's deadline is set by its first waiting candidate (capped at drain start + 20 s) and never extended. A later candidate on the same bridge whose deadline has already passed still reads once (a sweep that landed meanwhile serves it without waiting) but never waits; if nothing newer is there it holds `PROTECTIVE_HOLD_WAIT_BUDGET_USED` instead of a misleading "within 0s" (finding F5).
4. **Poll loop** (`PROTECTIVE_POLL_MS = 1_000`): read the row by the 9-field scope, the connection and the ticket's commands (re-read each poll); the bridge is re-verified on the re-read connection (`verifyProtectiveBridge`, held as its own reason with `stage: "wait"`); only ticket commands on this position's bridge and login count (`sameAccountTicketCommands`, unattributed rows kept); a ticket command in flight holds `PROTECTIVE_HOLD_MANUAL_COMMAND_IN_FLIGHT` at once (finding F8); then evaluate section 2 with `mustBeAfterMs = heldAtMs`. Terminal reasons (closed, row missing, absent at broker, invalid/future timestamp, bridge offline) hold immediately; `_NOT_NEWER` / `_STALE` and the other evidence reasons keep polling; after the loop a non-ok verdict holds (`if (!v.ok) return hold(…)`): `PROTECTIVE_HOLD_NO_FRESH_SWEEP` (or `_WAIT_BUDGET_USED`) when nothing newer arrived, otherwise the last specific reason (for example `_PREDATES_COMMAND` when a manual modify kept superseding the evidence). The newest ticket-command event time seen travels with the claim (`evidence.ticketCommandAt`).
5. **Fresh decision** on the sweep row with the same inputs as the ordinary path; no protective trigger → `PROTECTIVE_HOLD_TRIGGER_CLEARED` (INFO). If the trigger changed, the fresh one wins.
6. **Identity**: `verifyProtectivePosition` (section 5).
7. **Bridge identity again** on the final connection record (`verifyProtectiveBridge`, finding F3): a heartbeat during the wait can change account number, server name, account type, capability or revocation; any failure holds with that check's own reason and text (detail `stage: "final"`). Then **heartbeat fresh** (under 15 s) else `PROTECTIVE_BRIDGE_HEARTBEAT_NOT_FRESH` — avoids claiming a command the dispatch gate would block.
8. **Intent + geometry**: `CLOSE { side, volume: row.volume }` or `MODIFY_STOP { side, newStopLoss, newTakeProfit: row.takeProfit }`; `evaluateProtectiveGeometry` (section 4). Because volume and take-profit are taken from the same fresh row as the position facts, the reverse, partial and take-profit rules cannot fail here; what this step actually proves is the stop rule (strictly tighter, not removed, not at/through price). Volume and take-profit are enforced downstream (section 4, "Where volume and take-profit are enforced").
9. **Claim (CAS)**: `pendingManagement` gains `protective: { trigger, heldReason, heldAtMs, evidence: { lastSyncedAt, sweepAt, heartbeatAt, serverName, currentPrice, volume, stopLoss, takeProfit, ticketCommandAt } }` (`executionLifecycle.ts:15-38`); a lost CAS holds `PROTECTIVE_HOLD_CLAIM_RACE`.
10. **Dispatch** through the factored `dispatchClaimedManagement` (`livePositionManager.ts:169`): audit `MANAGEMENT_DISPATCH_INTENT` with `afterState.protective` (timing fields in section 10), then `guardianInstantManage({ ruleId: "self-trade-manage", ... })` exactly as the ordinary path. Everything downstream is unchanged and still runs: `buildManagementTarget`, `createLiveOpsDraft` (arming, kill switch, geometry), Risk Governor tighten-only, Phase B gates, `claimManagementCommand` (section 8), mailbox pickup, EA `ArxManagementPreflight`.
11. **Outcome bookkeeping** is the existing code: a refusal without `commandId` rolls the claim back (`PROTECTIVE_HOLD_PIPELINE_REFUSED`); a `commandId` is linked (+ `closeCommandId` for EXIT); an uncertain submission keeps the claim. A refusal *after* the command row exists (for example a gate block) is reported truthfully as `PROTECTIVE_HOLD_REFUSED_WITH_COMMAND` with an audit row and counted as held, not acted (finding F6); the command link is kept for reconciliation, never rolled back here. When the refusal reason is itself a protective reason (the final-claim parity of section 8: `PROTECTIVE_HOLD_MANUAL_COMMAND_IN_FLIGHT`, `PROTECTIVE_TICKET_COMMAND_AFTER_EVIDENCE`, a stale or absent row, a stop through price), the hold carries that reason (`stage: "final-claim"`), its text names the manual command (the ticket's commands are re-read once to name it) and, when a command row exists, appends that the refused command is kept for reconciliation.

Lock order downstream is unchanged: bridge → execution → entry → position → command (`managementTarget.ts:350-357`); no network under locks.

## 4. Geometry predicates (pure, `lib/domain/src/self-trade/protectiveAction.ts`)

Hygiene: positive finite numbers only; `EPS_PRICE = 1e-9`; `volTol(v) = max(1, |v|) · Number.EPSILON · 16`. A `side` other than exactly `"BUY"`/`"SELL"`, an intent with an unknown `kind`, a missing or extra key (`closeVolume`, `volume` on MODIFY, `newTakeProfit` on CLOSE), or any non-finite/zero/negative/string number → `PROTECTIVE_GEOMETRY_INVALID`. Evaluation order of `evaluateProtectiveGeometry`: shape/side → reverse → partial → stop (removal first) → take-profit; first failure wins. Only `evaluateProtectiveGeometry` carries the whole guarantee. Each standalone predicate applies a subset of its rules in the same order, so it refuses only where the full geometry also refuses (domain cases "… refuses only where geometry refuses", finding F10). `doesNotReverse` and `doesNotLoosenStop` also name the same first reason; `doesNotIncreaseExposure` checks stop removal but not stop placement, so for a MODIFY that both loosens (or crosses price with) the stop and changes the take-profit it names `PROTECTIVE_TAKE_PROFIT_CHANGED` while the full geometry names `PROTECTIVE_STOP_NOT_TIGHTER` / `PROTECTIVE_STOP_THROUGH_PRICE` (both still refuse).

- **G1 `doesNotIncreaseExposure`** — rules reverse → partial → stop removal → take-profit. CLOSE must be the full volume on the position's side (`PROTECTIVE_WOULD_REVERSE` above, `PROTECTIVE_PARTIAL_NOT_SUPPORTED` below). MODIFY may not remove the stop (`PROTECTIVE_STOP_NOT_TIGHTER`, problem "stop removal": an unprotected position has unbounded risk) and must keep the take-profit (`PROTECTIVE_TAKE_PROFIT_CHANGED`; `null === null` allowed). The intent type admits no open, pending, reverse or close-by.
- **G2 `doesNotReverse`** — CLOSE side must match (`PROTECTIVE_SIDE_MISMATCH`) and volume must not exceed the position (`PROTECTIVE_WOULD_REVERSE`; on a netting account an over-volume close is an opposite-side market order).
- **G3 `doesNotLoosenStop`** — CLOSE: true. MODIFY: `newStopLoss === null` is a removal → `PROTECTIVE_STOP_NOT_TIGHTER`; the stop may never sit at or through price (BUY `s < p − EPS`, SELL `s > p + EPS`, else `PROTECTIVE_STOP_THROUGH_PRICE`, where `p` is the v154 snapshot price on the side the stop triggers); when a stop exists it must be strictly tighter (equal → `PROTECTIVE_STOP_NOT_TIGHTER`: a no-op must not spend a claim); a null current stop may be set.

Downstream the same constraints are enforced again by Guardian `authorizeManagement`, the Risk Governor tighten-only rule, `assertManagementGeometry` at draft/claim/transport and the EA preflight. New here: the through-price refusal and the no-op refusal.

**Where volume and take-profit are enforced (finding F9).** In the path the intent's volume and take-profit come from the same fresh row as the position facts, so G1/G2's volume rules and the take-profit pin are tautological there; they are real guarantees only of the pure predicates. The command that reaches the broker is constrained by:

- **Volume**: `buildManagementTarget` sets `target.volume = position.volume` and refuses unless the row volume equals the execution's intended volume and the entry is full-volume (`MANAGEMENT_POSITION_IDENTITY_CHANGED`, `managementTarget.ts:114-126`); `executeClose` refuses any `closeVolume` (`MANAGEMENT_INTENT_MISMATCH`, `instantTrade.ts:543-548`); `assertManagementGeometry` requires the command volume to equal the target at draft, final claim and transport; the target is rebuilt from the locked rows at the final claim and must deep-equal (`MANAGEMENT_TARGET_CHANGED`); the EA preflight re-checks volume against `PositionSelectByTicket`.
- **Take-profit**: a non-null `newTakeProfit` must equal `target.currentTakeProfit` (`MANAGEMENT_INTENT_MISMATCH`, `instantTrade.ts:543-548`). A **null** one is not pinned: `instantTrade.ts:646` falls back to the row's current take-profit (`intent.newTakeProfit ?? row.takeProfit`). That value is the same row `buildManagementTarget` read, `assertManagementGeometry` compares it with `target.currentTakeProfit` at draft and claim, and a change between draft and claim is `MANAGEMENT_TARGET_CHANGED`. So the take-profit sent is always the broker row's take-profit at draft time (a manual change made before the draft is kept, never removed), and the EA preflight checks it against the terminal. `instantTrade.ts` behaviour is unchanged for every caller.

## 5. Identity verification

`verifyProtectiveBridge(entry, execution, connection, heartbeat)` — order: connection present and `id === entry.bridgeConnectionId` (`PROTECTIVE_BRIDGE_UNVERIFIED`); `userId === executingUserId` (`_OWNER_MISMATCH`); `accountNumber === entry.accountLogin`, `brokerName === entry.brokerServer`, non-empty `serverName` (`_ACCOUNT_MISMATCH`); not revoked, token present (`_REVOKED`); `accountType` live/real (case-insensitive; null refuses) and `mode !== "MOCK"` (`_NOT_LIVE`); heartbeat online (`_OFFLINE`); `supportsManagementTargetV1` (`PROTECTIVE_HOLD_TERMINAL_UPGRADE_REQUIRED`). The domain function takes the heartbeat class as a label so the module stays import-free; the caller classifies with `heartbeatPolicy`.

`verifyProtectivePosition(execution, entry, row)` — order: row present (`PROTECTIVE_IDENTITY_ROW_MISSING`); `row.userId === executingUserId === entry.userId` (`_OWNER_MISMATCH`); same broker account as the entry (`_ACCOUNT_MISMATCH`); `brokerTicket` equal across row, execution and entry (`_TICKET_MISMATCH`); `row.sourceCommandId === entry.commandId` (`_SOURCE_COMMAND_MISMATCH`); broker-native symbol (`_SYMBOL_MISMATCH`); side (`_SIDE_MISMATCH`); volume within `volTol` of the intended volume (`_VOLUME_CHANGED`). Detail carries `{ field, expected, observed, rowId }`.

The row itself is read by `managementPositionScope` over all nine fields (row id, user, bridge, login, company, ticket, entry command, symbol, side), so a reused ticket on another account of the same user never matches (PostgreSQL case "the 9-field protective scope reads only the exact row when another account reuses the ticket").

MT5 `POSITION_IDENTIFIER` is not checkable: it is not ingested, there is no column and no migration is allowed. Compensating controls are the EA `ArxManagementPreflight` (`mt5-bridge/ArxManagementTarget.mqh:169-217`: real trade mode, login, server, `PositionSelectByTicket`, symbol/type/volume/SL/TP equality, re-check after selection) and `assertReceipt` on the result.

## 6. Hold reasons and their text

All 48 reasons in `PROTECTIVE_HOLD_REASONS` have operator text in `explainProtectiveHold(reason, detail)`; placeholders come from the redacted detail (`redactProtectiveDetail` drops keys matching token/hash/secret/apikey/password/credential), unknown placeholders render as "unknown", and `ageMs`/`waitedMs` are also offered as seconds. Representative texts:

| Reason | Text |
| --- | --- |
| `PROTECTIVE_HOLD_PLATFORM_STOP_ENGAGED` | The platform emergency stop is engaged ({sources}). Automatic closes and stop moves are refused by design; use the admin emergency close or the broker terminal. Broker-side stop and take-profit remain active. |
| `PROTECTIVE_HOLD_USER_NOT_ARMED` / `_USER_KILL_SWITCH` | Live trading is not armed / your live kill switch is engaged, so no automatic order can be created. Manual close/modify and broker-side stops are unaffected. |
| `PROTECTIVE_HOLD_TERMINAL_UPGRADE_REQUIRED` | This terminal's EA does not support exact-target management (supportsManagementTargetV1). Upgrade the EA or manage the position manually. |
| `PROTECTIVE_BRIDGE_*` | The bridge now reports account {login}@{server} ({mode}/{accountType}); the position was opened on {expectedLogin} at {expectedCompany}. Nothing is sent to a different account. |
| `PROTECTIVE_BRIDGE_OFFLINE` / `_HEARTBEAT_NOT_FRESH` | The MT5 bridge heartbeat is {ageSec}s old (offline after 60s) / live dispatch requires under 15s. With no heartbeat time: "The MT5 bridge has no recorded heartbeat (missing), so it cannot be verified online; nothing is sent." With a time ahead of the server clock: "The MT5 bridge heartbeat timestamp is {aheadSec}s ahead of the server clock, so its liveness is unverified; nothing is sent." Both still hold (finding F4; previously "-2s old" / "unknowns old"). |
| `PROTECTIVE_HOLD_NO_FRESH_SWEEP` | No broker position snapshot newer than {heldAt} arrived within {waitedSec}s (last snapshot {ageSec}s old). ARX will not close or move a stop from old data. Manual controls and the stop held at the broker remain active. |
| `PROTECTIVE_HOLD_WAIT_BUDGET_USED` | No broker position snapshot newer than {heldAt} is available, and the wait budget for this bridge was already used this cycle by an earlier held position (one sweep refreshes every position on the bridge). ARX re-checks next cycle. |
| `PROTECTIVE_HOLD_MANUAL_COMMAND_IN_FLIGHT` | A close/modify for this ticket ({commandId}, sent {sentAt}) is still in flight at the terminal and has neither filled nor been rejected. ARX will not act on top of a manual or pending order. |
| `PROTECTIVE_TICKET_COMMAND_AFTER_EVIDENCE` (final claim) | Another close/modify for this ticket ({commandId}) moved at {eventAt}, after the snapshot ({observedAt}) this action was justified by. The request is refused. |
| `PROTECTIVE_HOLD_REFUSED_WITH_COMMAND` | The live pipeline refused the request after command {commandId} was recorded: {pipelineReason}. The command is kept for reconciliation and is not retried. |
| `PROTECTIVE_HOLD_DEFERRED_TO_NEXT_CYCLE` (INFO) | Stop tightening is not urgent; it will be re-evaluated next cycle from a fresh snapshot. |
| `PROTECTIVE_OBSERVATION_*` | The latest snapshot is {ageMs}ms old / dated ahead of the server / has no usable time / was last written by a reconciler, not a complete terminal snapshot / is not newer than the hold at {heldAt} / predates a close or modify sent at {eventAt}. |
| `PROTECTIVE_SWEEP_MARKER_STALE` | The terminal's complete-snapshot marker is older than the row or too old; the row cannot be trusted as part of a full sweep. |
| `PROTECTIVE_POSITION_ABSENT_AT_BROKER` | The latest complete broker snapshot did not list ticket {ticket} (absent {count} sweep(s)). It may already be closed at the broker; reconciliation will confirm. No order was sent. |
| `PROTECTIVE_IDENTITY_*` | The broker position no longer matches the one this agent opened ({field}: expected {expected}, observed {observed}). Nothing is sent. |
| `PROTECTIVE_HOLD_TRIGGER_CLEARED` (INFO) | Fresh snapshot: price {p} no longer triggers {trigger}; no action. |
| `PROTECTIVE_GEOMETRY_*` | The proposed {action} would loosen or not tighten the stop / place the stop at or through price / change the take-profit / exceed the open volume / reduce size (no partial path) / act on the wrong side; refused. |
| `PROTECTIVE_HOLD_CLAIM_RACE` / `_PIPELINE_REFUSED` / `_OUTCOME_UNCERTAIN` / `_INTERNAL_ERROR` | Another cycle already claimed this position / the live pipeline refused the request before a command existed: {pipelineReason} / the submission outcome is unknown and the claim is kept for reconciliation / the protective path failed safely ({message}); nothing was sent. |
| `MANAGEMENT_PAUSED_AACI_REVIEW` (cycle-level) | Management for this agent is paused until the AACI chain review clears. |

Hold explanations are durable in the audit log, not in `managementState` (kept out so that a hold still leaves `managementState` untouched).

## 12. Explicit limits

1. The server can prove the EA read the broker's position list after the hold; it cannot prove the terminal is on the same account at execution. `ArxManagementPreflight` re-checks login/server/trade mode before and after `PositionSelectByTicket` but is not atomic (`ArxManagementTarget.mqh:204-217`).
2. No MT5 `POSITION_IDENTIFIER` server-side (not ingested, no column, no migration). Ticket reuse across accounts is defended by the account tuple and the 9-field scope; same-account ticket reuse is not detectable.
3. `brokerServer` on rows is the company label; the MT5 server name lives in the mutable heartbeat (`routes/mt5.ts:458`) and is pinned into the claim evidence (`serverName`), not into the row.
4. "Fresh" is not "connected": an EA whose terminal lost the trade server can still push snapshots with last-known prices; the heartbeat carries no `TERMINAL_CONNECTED`. EA-side follow-up.
5. No pull: evidence arrives only when the EA pushes (10 s in v154); while it does not push the path holds, which is also when the EA would not poll a command.
6. The v131 `currentPrice` basis (bid vs ask) is not documented in the payload; the through-price rule assumes the v154 convention (BID for BUY, ASK for SELL).
7. Broker execution (slippage, requote, partial fill, a broker-side SL firing between push and pickup) is unknown until the result report; settlement comes from evidence, never from elapsed time.
8. Between the final claim and EA pickup nothing server-side can halt the command; unchanged.
9. The cycle is operator-run (`routes/selfTradeAi.ts:163`); production protective latency is bounded by how often cycles run, not by this path.
10. `_PREDATES_COMMAND` after a manual modify delays a protective EXIT by up to one sweep cadence, and a manual command still in flight holds it for the cycle (`_MANUAL_COMMAND_IN_FLIGHT`); accepted (acting on a snapshot that ignores a human's just-sent change is worse). A command stuck in `LIVE_UNKNOWN` / `LIVE_RECONCILIATION_REQUIRED` keeps holding the path until reconciliation settles it.
11. The advisory broker-quote cross-check from the spec (symbol-keyed `getQuote`, never gating) is not implemented in this slice; the path relies on the sweep row's price only.
12. Legacy EAs without `supportsManagementTargetV1` never receive protective commands; the hold says so.
13. `SYMBOL_TRADE_STOPS_LEVEL` is unknown server-side; a stop too close to price is rejected by the broker and resolves as `REJECTED`.
14. The optional `protectiveHold` join on `GET /self-trade-ai/executions` is not implemented; holds are read from the audit route and the cycle result.
15. Hold explanations are durable in the audit log, not in `managementState`.
16. A null take-profit on a protective stop move is not pinned by the intent; the pipeline uses the row's take-profit at draft time, which the management target pins (section 4).
17. `PROTECTIVE_HOLD_REFUSED_WITH_COMMAND` is not retried by the path; the command row and claim link stay for reconciliation, as for the ordinary path.
18. The ticket-command read is the manager's existing one (user + command type + `payload->>'brokerTicket'`); the protective path and the final claim then keep only commands on the position's bridge and login, so a same-numbered ticket on another account of the same user no longer holds this position. A command with no recorded bridge or login is still counted (fail closed). The ordinary path's ordering check is unchanged and still uses every row.
